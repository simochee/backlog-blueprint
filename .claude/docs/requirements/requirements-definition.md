# backlog-blueprint 要件定義

最終更新: 2026-09-17
前提となる要求: [requirement-design.md](requirement-design.md)
前提となる API 仕様: [../research/backlog-api-constraints.md](../research/backlog-api-constraints.md)
参考にした先行事例: [../design/syntax-reference-github.md](../design/syntax-reference-github.md)

## 1. 用語

| 用語 | 意味 |
| --- | --- |
| マニフェスト | プロジェクト設定を宣言した Yaml ファイル。1ファイル = 1プロジェクト |
| 検証 (validate) | マニフェストとスペースの実状を突き合わせ、適用可能かを判定する段階 |
| 計画 (plan) | 適用したら何が起きるかの一覧。Backlog を一切変更しない |
| 適用 (apply) | 計画を実際に Backlog API に流す段階 |
| 同定キー | Backlog 上の既存リソースとマニフェストの記述を対応付けるキー。**本ツールでは `name`** |

## 2. マニフェスト仕様

### 2.1 形式

| 項目 | 決定 | 理由 |
| --- | --- | --- |
| ファイル単位 | 1ファイル = 1プロジェクト | プロジェクト単位でレビュー・適用したい。ファイル名と対象が1対1で対応する |
| バージョニング | `$schema` にバージョン入りの URL を書く。実体は `https://simochee.github.io/backlog-blueprint/schema/<version>/project.json` | 詳細と選定理由は [manifest-versioning.md](../design/manifest-versioning.md) |
| キー名 | Backlog API のフィールド名をそのまま使う（camelCase） | GitHub の設定 IaC が採る「API の命名をそのまま使う」原則に倣う。API リファレンスと Yaml とエラーメッセージが1対1で対応する |
| 色の表記 | `"#ea2c00"` のように**必ず引用符で囲む** | `#` から始まる値は引用符が無いと YAML のコメントとして解釈される。先行事例で頻出する罠 |
| 未知キー | **エラー**（strict parse） | 新しい Yaml を古い CLI に食わせたとき黙って無視されるのが最悪。タイプミスも同時に防げる |
| 変数展開 | `${ENV_NAME}` を環境変数から展開 | Webhook URL などの秘匿値をコミットさせない |
| 表示順 | Yaml の記述順を表示順とする（[保証できる範囲はリソースによる](#24-表示順の扱い)） | 「書いてある通りになる」が最も予測しやすい。表示順を別キーで持つと二重管理になる |
| リクエスト数 | 書き方でリクエスト数（＝所要時間）が変わる。[削減できる書き方](#25-リクエスト数を減らす書き方)を推奨形とする | 更新系 API は1秒に1件しか流せないため、リクエスト数がそのまま体感速度になる |

### 2.2 構造

サンプル: [manifest-example.yaml](manifest-example.yaml)

| トップレベルキー | 内容 | 削除の扱い |
| --- | --- | --- |
| `key` | プロジェクトキー。`^[A-Z0-9_]+$` | — |
| `name` | プロジェクト名 | — |
| `settings` | プロジェクト基本設定（[対応項目](../research/backlog-api-constraints.md#プロジェクト基本設定)） | — |
| `issueTypes` | 課題種別 | Yaml に無いものは削除 |
| `statuses` | ステータス。既定4つを必ず含める | Yaml に無いカスタムは削除 |
| `categories` | カテゴリー | Yaml に無いものは削除 |
| `milestones` | マイルストーン（版） | Yaml に無いものは削除 |
| `customFields` | カスタム属性 | Yaml に無いものは削除 |
| `access` | `teams` / `members` / `administrators` の3キー（[詳細](#26-access-の仕様)） | Yaml に無いものは削除 |
| `webhooks` | Webhook（[詳細](#27-webhooks-の仕様)） | Yaml に無いものは削除 |

**すべてのリソースで「Yaml に書いていないものは削除」する。** 依頼者の選択による。
宣言的であること（Yaml が現実の完全な写像であること）を優先し、
「知らないうちに増えた設定」が残り続ける状態を作らない。

### 2.3 同定キーを `name` にすることの帰結

Backlog 上のリソース ID を Yaml に書かないため、名前でマッチングする。

- 名前を変更すると「旧名を削除 + 新名を作成」と解釈される
- これは差分適用なら課題の紐付けが壊れる危険な挙動だが、
  **本ツールは課題0件のプロジェクトしか対象にしない**ため実害がない
- 逆に言えば、この設計は非スコープ（差分取り込み）と不可分に結びついている。
  将来 差分適用を入れるなら同定キーの設計からやり直しになる

### `oldname` によるリネーム

削除＋作成の2リクエストを、更新1リクエストに減らすための任意キー。
GitHub の [safe-settings](https://github.com/github/safe-settings) が同じ仕組みを持つ。

```yaml
issueTypes:
  - name: 調査
    oldname: その他      # 既定の「その他」をリネームして使い回す
    color: "#2779ca"
```

| 決定 | 内容 |
| --- | --- |
| O-1 | `oldname` は `issueTypes` / `statuses` / `categories` / `milestones` / `customFields` で使える |
| O-2 | `oldname` のリソースが存在すれば**更新**、存在しなければ通常どおり**作成**する |
| O-3 | `oldname` のリソースが存在しない場合はエラーにしない |

O-3 は冪等性（NFR-4）のため。1回目の適用でリネームが済むと、2回目は `oldname` の対象が
存在しなくなる。ここでエラーにすると、適用後の Yaml をそのまま再適用できなくなる。

Yaml が「あるべき姿」を表し、`oldname` は移行元のヒントに過ぎない、という関係を保つ。
適用後に `oldname` を消しても消さなくても、結果は変わらない。

### 2.4 表示順の扱い

表示順を変更する API があるのはステータスだけ。他は**作成順で決まり、後から並べ替えられない**。

| リソース | 並べ替え API | 記述順の保証 |
| --- | --- | --- |
| ステータス | `PATCH /projects/:key/statuses/updateDisplayOrder`（一括・1リクエスト） | **保証する** |
| 課題種別 | **無い** | 保証しない（既存の順序を保ち、新規は末尾に付く） |
| カテゴリー | **無い** | 同上 |
| マイルストーン | **無い** | 同上 |
| カスタム属性 | **無い** | 同上 |

課題種別で Yaml の記述順を厳密に再現しようとすると、既定の4つを全削除して作り直すしかなく、
リクエスト数が跳ね上がる。**表示順のために削除・再作成はしない。**
plan では「適用後に実際どう並ぶか」を表示し、Yaml の記述順と一致しない場合は警告する（V-A15）。

ステータスには API 側の順序制約がある（V-A14）。

- 「未対応」が先頭
- 「完了」が末尾
- 「処理中」は「処理済み」より前

### 2.5 リクエスト数を減らす書き方

更新系 API は直列・1秒間隔なので、**リクエスト数 ≒ 所要時間（秒）**。
マニフェストの書き方でこれが大きく変わるため、推奨形を仕様として定める。

| # | 手段 | 効果 |
| --- | --- | --- |
| L-1 | 個人ではなく**チーム**で参加させる | 個人20人 = 20リクエスト → チーム1つ = 1リクエスト |
| L-2 | **既定値と一致する内容を書く** | 差分ゼロなら作成も削除も更新も起きず 0リクエスト |
| L-3 | 1リクエストに複数乗るものはまとめる | `settings` は1リクエスト、ステータス表示順は一括、`applicableIssueTypes[]` と `activityTypeIds[]` も1リクエストに複数 |
| L-4 | 冗長な記述をツール側で畳む | チーム経由で参加済みの人を `members` に書かせない。`administrators` の自動参加も重複を打たない |
| L-5 | 一致している既存リソースは触らない | 名前も色も同じなら `PATCH` を打たない |
| L-6 | **`oldname` で既定リソースをリネームして使い回す** | 削除＋作成の2リクエスト → 更新1リクエスト |

L-2 が最も効く。既定の課題種別（タスク / バグ / 要望 / その他）をそのまま活かす Yaml なら
作成4件・削除4件の計8リクエストがまるごと消える。
**「クリーンアップする」という選択には、既定を捨てるぶんの実行時間というコストがある。**
組織標準の雛形を設計するときは、既定と揃えられる部分は揃えるほうが速い。

L-2 と L-6 は組み合わせて効く。既定の課題種別4つを、そのまま使う／`oldname` でリネームする／
削除する、の順にコストが上がる。雛形を設計するときは上から検討する。

plan では「更新系 N 件 / 推定 N 秒」を必ず表示し、この判断材料を与える（FR-3.4）。

### 2.6 `access` の仕様

```yaml
access:
  teams:          # チーム名。1チーム = 1リクエスト
    - 開発チーム
    - QA
  members:        # どのチームにも属さない個人。ユーザーID（ログインID）
    - suzuki
  administrators: # プロジェクト管理者にする個人。ユーザーID
    - yamada
```

| 決定 | 内容 | 理由 |
| --- | --- | --- |
| A-1 | チームと個人は**別キー**にする | 1つのリストに混ぜると、名前を見てどちらか判別できない。解決先の API も別 |
| A-2 | 管理者は `administrators` の独立リストにする | Backlog API はプロジェクト管理者を**個人単位でしか付けられない**。チームごと管理者にはできないので、チームと同じ階層に混ぜると表現できない構造になる |
| A-3 | `administrators` に書いた人が未参加なら、**自動で個人参加させる** | `members` と `administrators` に同じ名前を2回書かせない。plan には自動参加を明示する |
| A-4 | チーム経由で参加している人を `members` に書く必要はない | 書いても動くが、個人参加としても登録されるぶんリクエストが1件増える。V-A16 で警告する |

**削除判定には `GET /projects/:key/users?excludeGroupMembers=true` を使う。**
既定値（false）ではチーム経由の参加者も含まれるため、
「Yaml の `members` に無いから削除」と判定するとチームの所属者を個人として削除しようとしてしまう。

### 2.7 `webhooks` の仕様

```yaml
webhooks:
  - name: Slack 通知
    description: 課題の追加・更新を Slack に流す
    hookUrl: ${SLACK_WEBHOOK_URL}
    events:
      - issueCreated      # 名前で書ける
      - issueUpdated
      - 50                # CLI が知らない新しいイベントは数値で書ける

  - name: 監査ログ
    hookUrl: ${AUDIT_URL}
    events: all           # API の allEvent: true に対応する
```

| 決定 | 内容 | 理由 |
| --- | --- | --- |
| W-1 | `events` は**イベント名と数値 ID の両方**を受け付ける | 名前で読めることと、Backlog が新イベントを追加しても CLI を更新せず使えることを両立させる |
| W-2 | `events: all` を API の `allEvent: true` に対応させる | 全イベント指定を明示的に書けるようにする |
| W-3 | キー名を `activityTypeIds` ではなく `events` にする | 値が ID だけでなくなるため、`activityTypeIds` は実態と合わない。[G-3（API の命名をそのまま使う）](../design/syntax-reference-github.md#1-構造の取り方)から外れる唯一の箇所 |
| W-4 | **未知の名前はエラー、未知の数値は警告** | 名前のタイプミスは確実に間違いなので止める。数値は前方互換のために通す |
| W-5 | plan では数値に名前を添えて表示する | `events: 1 (Issue Created), 2 (Issue Updated)` |

イベント名は [activityTypeId 一覧](../research/backlog-api-constraints.md#activitytypeid-の一覧)の
英語名を camelCase にしたもの（`Issue Created` → `issueCreated`）。
JSON Schema に名前の enum と各値の説明を持たせ、エディタ補完で意味が出るようにする。

## 3. 機能要件

### FR-1 マニフェストの読み込み

| ID | 要件 |
| --- | --- |
| FR-1.1 | Yaml をパースし、スキーマに従って型検証する |
| FR-1.2 | 未知のキーが存在したらエラーにする |
| FR-1.3 | `${NAME}` を環境変数から展開する。未定義ならエラー |
| FR-1.4 | JSON Schema を GitHub Pages に配布し、エディタ補完が効くようにする |

### FR-2 検証

| ID | 要件 |
| --- | --- |
| FR-2.1 | 適用を開始する**前に**すべての検証を行い、1件でも違反があれば何も適用せず中断する |
| FR-2.2 | 違反は「どのキーが」「なぜダメか」「どう直すか」を示す |
| FR-2.3 | 違反は1件目で止めず、検出できるものはすべて列挙する |

FR-2.1 は依頼者要求 R-2 そのもの。「実行してみたら途中で消せないものが出てきた」を起こさない。
FR-2.3 は、直して再実行するたびに次のエラーが出るループを避けるため。

### FR-3 計画（dry-run）

| ID | 要件 |
| --- | --- |
| FR-3.1 | `plan` は Backlog に対して読み取り（GET）しか行わない |
| FR-3.2 | 作成・更新・削除される対象を人間向けに一覧表示する |
| FR-3.3 | 削除については**振替先**を併記する |
| FR-3.4 | 更新系 API の件数から所要時間の見積もりを表示する |
| FR-3.5 | `--output json` で機械可読な計画を出力する |
| FR-3.6 | `${ENV}` で展開された値は出力時にマスクする |

### FR-4 適用

| ID | 要件 |
| --- | --- |
| FR-4.1 | 適用前に必ず検証と計画の算出を行う |
| FR-4.2 | [適用順序](#6-適用順序)に従って更新系 API を直列に実行する |
| FR-4.3 | API エラーが起きたら**即座に中断**する。ロールバックはしない |
| FR-4.4 | 中断時は「適用済みの操作」「未適用の操作」「失敗した操作とエラー内容」を出力する |
| FR-4.5 | 進捗（N/M 件目・現在の操作）を逐次表示する |

FR-4.3 は依頼者の選択。ロールバックは削除不可リソースの存在により原理的に完全にはできず、
「中途半端に戻した状態」を作るだけなので、状態を正直に報告して人間に判断させる。

### FR-5 認証と権限

| ID | 要件 |
| --- | --- |
| FR-5.1 | 認証は API キー。CLI は環境変数（例: `BACKLOG_API_KEY`）、Web UI は入力欄から受け取る |
| FR-5.2 | スペースのドメイン（例: `example.backlog.com`）を指定できる |
| FR-5.3 | 実行開始時に `GET /users/myself` で実行者を確認する |
| FR-5.4 | 実行者がスペース管理者でなければ、新規・既存を問わず中断する |

FR-5.4 は「既存プロジェクトならプロジェクト管理者でよい」という当初案を破棄した結果。
ステータス操作がスペース管理者を要求するため、権限で分岐させると
「ステータスを書いた瞬間に動かなくなる」直感に反するツールになる。

### FR-6 CLI

| ID | 要件 |
| --- | --- |
| FR-6.1 | `npx @simochee/backlog-blueprint` で実行できる |
| FR-6.2 | `plan` / `apply` のサブコマンドを持つ |
| FR-6.3 | 終了コードで結果を区別する |

終了コード:

| コード | plan | apply |
| --- | --- | --- |
| 0 | 差分なし | 成功 |
| 1 | エラー（検証違反・認証・通信） | エラー |
| 2 | 差分あり | （未使用） |

GitHub Action・Docker イメージ・PR コメント機能は提供しない。
`--output json` があれば利用者側で組める、という判断。

### FR-7 Web UI

| ID | 要件 |
| --- | --- |
| FR-7.1 | static hosting で動作する（サーバを持たない） |
| FR-7.2 | Yaml を貼り付ける入力欄、スペースドメインと API キーの入力欄を持つ |
| FR-7.3 | plan の結果を表示し、確認のうえ apply できる |
| FR-7.4 | API キーをメモリ上のみで保持し、localStorage 等に永続化しない |
| FR-7.5 | 環境変数が使えないため、`${ENV}` を含む Yaml では値の入力を求める |

Yaml を GUI フォームから生成する機能、既存プロジェクトからの逆生成は初期スコープ外。

## 4. 非機能要件

| ID | 要件 | 理由 |
| --- | --- | --- |
| NFR-1 | 更新系 API は直列で、**1秒以上の間隔**をあけて実行する | 公式推奨。並列化は選択肢にない |
| NFR-2 | `429` を受けたら `X-RateLimit-Reset` まで待って再試行する（上限回数あり） | レート制限超過で失敗させない |
| NFR-3 | API キーをログ・計画出力・エラーメッセージに出さない | CI ログへの漏洩を防ぐ |
| NFR-4 | 同じマニフェストを2回適用しても結果が変わらない（冪等） | 中断後の再実行を安全にする |
| NFR-5 | core パッケージは `fetch` 以外のランタイム依存を持たない | Node とブラウザで同一ロジックを動かすため |
| NFR-6 | 検証・計画のロジックは CLI と Web UI で同一のコードを使う | 「CLI では通るが Web では落ちる」を構造的に作らない |
| NFR-7 | **マニフェストを置いたリポジトリへの push 権限が、実質的にスペース管理者権限になる**ことを README で警告する | 実装では防げない。CI に置く API キーはスペース管理者のものなので、そのリポジトリに push できる人は任意のプロジェクト設定を書き換えられる。[先行事例](../design/syntax-reference-github.md#33-設定リポジトリへの-push-権限が管理者権限になる)でも同じ警告が出ている |
| NFR-8 | リソース種別ごとに独立した reconciler（現状取得 → 差分算出 → 適用）として実装する | リソース追加が「ファイルを1つ足して適用順序に並べる」だけで済む。plan と apply が同じ `Action[]` を扱うので「plan に出ないのに apply で起きる」が構造的に消える |
| NFR-9 | CLI / Web UI / JSON Schema のメッセージは**英語のみ**とする | OSS として公開する前提。Backlog 自体が多言語展開しており、利用者層を日本語圏に狭めない。i18n の仕組みは入れない |

## 5. 検証仕様

FR-2 の具体。**すべて適用開始前に判定する。**

### 5.1 静的検証（マニフェストだけで判定できるもの）

| ID | 検証内容 | 結果 |
| --- | --- | --- |
| V-A1 | 未知のキーが存在しない | エラー |
| V-A2 | 必須キー（`key` / `name`）が存在する | エラー |
| V-A3 | プロジェクトキーが `^[A-Z0-9_]+$` に一致する | エラー |
| V-A4 | `${ENV}` がすべて解決できる | エラー |
| V-A5 | 各リソース内で `name` が重複していない | エラー |
| V-A6 | **既定ステータス4つ（未対応・処理中・処理済み・完了）がすべて `statuses` に含まれる** | エラー |
| V-A7 | ステータス総数が 12（既定4 + カスタム8）以下 | エラー |
| V-A8 | ステータスの色が10色パレットに含まれる | エラー |
| V-A9 | `issueTypes` が1件以上ある | エラー |
| V-A10 | `customFields[].applicableIssueTypes` が `issueTypes` に存在する名前を参照している | エラー |
| V-A11 | カスタム属性の型ごとの必須パラメータが揃っている（リスト型の `items` など） | エラー |
| V-A12 | `settings.grandchildIssueEnabled` が真なら `settings.subtaskingEnabled` も真 | エラー |
| V-A13 | `access.teams` / `access.members` / `access.administrators` の各リスト内に重複が無い | エラー |
| V-A14 | ステータスの並びが API の順序制約を満たす（未対応が先頭・完了が末尾・処理中が処理済みより前） | エラー |
| V-A15 | 課題種別・カテゴリー・マイルストーン・カスタム属性の記述順が、適用後の表示順と一致する | 警告 |
| V-A16 | `access.members` に、チーム経由で参加済みの人が書かれていない | 警告 |
| V-A17 | `oldname` が同一リソース内の他要素の `name` と衝突していない | エラー |
| V-A18 | 色の指定が文字列として解釈されている（引用符の付け忘れで `null` になっていない） | エラー |

**V-A6 と V-A9 が依頼者要求 R-2 の中核。**
「消せないもの」＝既定ステータス、「0件にできないもの」＝課題種別。
この2つを検証段階で必ず止める。

### 5.2 スペース検証（API で実状を確認して判定するもの）

| ID | 検証内容 | 結果 |
| --- | --- | --- |
| V-B1 | API キーが有効である（`GET /users/myself` が成功する） | エラー |
| V-B2 | 実行者がスペース管理者である | エラー |
| V-B3 | 対象プロジェクトが既に存在する場合、**課題件数が0である**（`GET /issues/count`） | エラー |
| V-B4 | `access` に書いたユーザー ID がスペースに存在する | エラー |
| V-B5 | `access` に書いたチーム名がスペースに存在する | エラー |
| V-B6 | **実行者自身がプロジェクト管理者から外れる定義になっていない** | エラー |
| V-B7 | 既存プロジェクトの削除対象リソースに対して、振替先が計画上決定できる | エラー |
| V-B8 | 更新系のレート制限残量が計画の操作数以上ある | 警告 |

V-A14 は API の制約をそのまま検証に落としたもの。適用の最後で表示順更新だけが失敗するのを防ぐ。

V-A15 と V-A16 を警告に留めるのは、どちらも実害が無いため。
前者は並び順が期待と違うだけ、後者はリクエストが1件増えるだけで、中断する理由がない。

V-B6 は、メンバーを削除対象に含めた結果として生まれる事故。
自分を締め出すと以後 API でもその設定を直せなくなる（スペース管理者なら復旧可能だが、
プロジェクト管理者の付け外しに気付けない）。明示的に止める。

V-B8 を警告に留めるのは、待てば解消するため。中断する理由がない。

### 5.3 エラー出力の形

メッセージは英語（NFR-9）。

```
$ npx @simochee/backlog-blueprint apply -f projects/PROJ_A.yaml

2 validation errors. Nothing has been applied.

ERROR [V-A6] statuses: default statuses cannot be deleted
  missing default status: 処理済み
  → add "処理済み" to statuses, or rename it with oldname

ERROR [V-B3] key: project already has issues
  PROJ_A: 43 issues
  → only projects with zero issues can be targeted
```

ステータス名や課題種別名など、**利用者が Backlog 上で付けた名前はそのまま表示する**。
翻訳の対象はツールが発するメッセージだけ。

## 6. 適用順序

削除 API が振替先を要求すること、カスタム属性が課題種別 ID を参照することから、
**追加を先、削除を後**にする以外の順序は成立しない。

| # | フェーズ | 操作 |
| --- | --- | --- |
| 0 | 検証 | セクション5のすべて。1件でも違反があればここで終了 |
| 1 | プロジェクト | 未作成なら `POST /projects`、既存なら `PATCH /projects/:key` |
| 2 | 課題種別 | 追加 → 更新 → 削除（振替先 = 定義の先頭の課題種別） |
| 3 | ステータス | カスタムを追加 → 更新 → 定義に無いカスタムを削除（振替先 = 未対応）→ 表示順を確定 |
| 4 | カテゴリー | 追加 → 更新 → 削除 |
| 5 | マイルストーン | 追加 → 更新 → 削除 |
| 6 | カスタム属性 | 追加 → 更新 → 削除（フェーズ2の課題種別 ID が確定している必要がある） |
| 7 | チーム・メンバー・管理者 | チーム追加 → 個人追加（`administrators` の未参加者を含む）→ 管理者付与 → 管理者解除 → 個人削除 → チーム削除 |
| 8 | Webhook | 追加 → 更新 → 削除 |

既定ステータス4つはフェーズ3で**何もしない**。削除できず、定義に含まれることは V-A6 で保証済み。
表示順の更新はフェーズ3の最後に1リクエストだけ流す（`statusId[]` に全ステータスを渡す必要がある）。

フェーズ7で削除対象を判定する際は、必ず `excludeGroupMembers=true` で個人参加者だけを取得する。
順序が「追加が先・削除が後」なのは、実行者自身が一時的にプロジェクトから外れる瞬間を作らないため。

> 既定ステータスのリネームが可能だと判明した場合、フェーズ3の設計と V-A6 の要否が変わる。
> [未検証事項](../research/backlog-api-constraints.md#未検証事項の一覧) を参照。

## 7. アーキテクチャ

```
packages/
  core/    パース・検証・plan 算出・apply 実行
           fetch のみに依存し、Node とブラウザの両方で動く
  cli/     npx backlog-blueprint（環境変数・ファイル IO・終了コード）
  web/     Vite SPA。static hosting に配置
  schema/  JSON Schema の生成物
```

検証・計画ロジックを core に閉じ込め、cli と web は「入出力の違い」だけを担う。
Go CLI + TypeScript Web という案は、検証ロジックを2回実装することになり
「CLI では通るが Web では落ちる」が構造的に発生しうるため採らない。

`core/resources/` はリソース種別ごとに1ファイルとし、それぞれが
「現状取得 → 差分算出 → 適用」を実装する（NFR-8）。

### 7.1 配布

| 対象 | 配布先 |
| --- | --- |
| CLI | npm `@simochee/backlog-blueprint`。実行ファイル名は `backlog-blueprint` |
| Web UI | GitHub Pages `https://simochee.github.io/backlog-blueprint/` |
| JSON Schema | GitHub Pages `https://simochee.github.io/backlog-blueprint/schema/<version>/project.json` |

```
https://simochee.github.io/backlog-blueprint/
├── index.html                      Web UI
└── schema/
    ├── 0.1.0/project.json
    └── 0.2.0/project.json          過去バージョンは消さない
```

`$schema` の URL に含まれるバージョンは npm パッケージの semver と一致させる
（[バージョニング方針 D-2](../design/manifest-versioning.md#3-本プロジェクトの決定)）。

**リリース時に npm publish と Pages デプロイを必ず同時に行う。**
スキーマだけデプロイし忘れると、利用者のエディタで `$schema` が 404 になり
補完が黙って効かなくなる。CI で同一ジョブにまとめ、片方だけ成功する状態を作らない。

## 8. 受け入れ基準

| ID | シナリオ |
| --- | --- |
| AC-1 | 存在しないプロジェクトキーのマニフェストを apply すると、プロジェクトが作成され、課題種別・ステータス・カテゴリー・マイルストーン・カスタム属性・メンバー・Webhook が定義通りになっている |
| AC-2 | 初期状態の課題種別（タスク/バグ/要望/その他）が定義に無ければ、適用後に残っていない |
| AC-3 | 既定ステータスを1つ省いたマニフェストを plan すると、V-A6 のエラーで中断し、Backlog は一切変更されていない |
| AC-4 | 課題が1件あるプロジェクトに apply すると、V-B3 のエラーで中断し、Backlog は一切変更されていない |
| AC-5 | 一般ユーザーの API キーで apply すると、V-B2 のエラーで中断する |
| AC-6 | plan は Backlog を変更しない。plan の直後に同じ内容の plan を実行しても結果が同じ |
| AC-7 | apply の途中で API エラーが起きると、そこで停止し、適用済み／未適用の一覧が出力される |
| AC-8 | apply 成功後に同じマニフェストを plan すると「差分なし」になり、終了コードが 0 になる |
| AC-9 | `${SLACK_WEBHOOK_URL}` を含むマニフェストで、環境変数が未定義なら V-A4 のエラーになる |
| AC-10 | plan / apply の出力とログのどこにも API キーが現れない |

## 9. 残る未検証事項

決定待ちの論点は解消済み。残るのは**実スペースで叩かないと分からない API の挙動**だけ。
実装着手前に確認し、判明した内容をここと [API 制約](../research/backlog-api-constraints.md)に反映する。

| # | 確認すること | 判明したら見直す箇所 |
| --- | --- | --- |
| 1 | 既定ステータス（未対応 / 処理中 / 処理済み / 完了）をリネーム・色変更できるか | リネーム可なら V-A6 を「`oldname` で参照していれば可」に緩和し、適用フェーズ3を見直す |
| 2 | プロジェクト管理者の付与に、対象が事前にプロジェクト参加者である必要があるか | 必要なら `access` の A-3（自動参加）が必須要件になる |
| 3 | 既定の課題種別4つ（タスク / バグ / 要望 / その他）の正確な色 | 雛形で L-2（既定と一致させて0リクエスト）を実践するために要る |
| 4 | CORS プリフライトの実挙動と、ブラウザから API キーを渡す方法 | 成立しなければ Web UI（FR-7）の前提が崩れる |
| 5 | `roleType` の数値と役割の対応 | V-B2（スペース管理者判定）の実装に直結する |
| 6 | カテゴリー・マイルストーンの表示順が何で決まるか | §2.4 の表を確定させる |

1 と 4 は結論次第で仕様が変わる。**4 は Web UI の成立条件**なので最優先で確認する。
