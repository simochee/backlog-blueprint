# backlog-blueprint 要求設計

最終更新: 2026-09-17 / 依頼者: @lollipop-onl

## 1. これは何か

Backlog のプロジェクト設定を Yaml で宣言し、CLI または Web UI から Backlog API 経由で
実際のプロジェクトに反映するツール。Infrastructure as Code の考え方をプロジェクト設定に適用する。

```
projects/PROJ_A.yaml  ──[ validate ]──[ plan ]──[ apply ]──▶  Backlog Space
                            │            │          │
                         中断できる    差分を見せる  API を直列に叩く
```

## 2. 解きたい問題

Backlog のプロジェクト設定は GUI の手作業でしか作れない。結果として次が起きている。

| 問題 | 具体的に困ること |
| --- | --- |
| 再現性がない | 「前のプロジェクトと同じ設定で」が手作業のコピーになる。抜けや揺れが必ず出る |
| レビューできない | 設定変更が誰の判断でいつ行われたか残らない。組織標準からの逸脱に気付けない |
| 標準化が効かない | 組織の雛形を配れない。ドキュメントに「こう設定してください」と書いて祈るしかない |
| 立ち上げが遅い | 課題種別・ステータス・カテゴリー・カスタム属性を毎回 GUI でポチポチ作る |

## 3. 提供する価値

- **雛形の配布**: 組織標準の Yaml を1つ置けば、誰でも同じ設定のプロジェクトを立ち上げられる
- **レビュー可能性**: 設定が差分としてレビューでき、決定の理由が Git に残る
- **確認してから実行**: apply の前に plan で「何を作り、何を消すか」を必ず見られる
- **誰でも使える**: Yaml を書けない人でも Web UI に貼り付けて実行できる

## 4. 利用者

| ID | 役割 | 使い方 | 権限 |
| --- | --- | --- | --- |
| P1 | スペース管理者 / PMO | 組織標準の Yaml を設計・保守し、新規プロジェクトに適用する | スペース管理者 |
| P2 | プロジェクト立ち上げ担当 | 標準 Yaml をコピーし、名前とキーを変えて CLI で適用する | スペース管理者 |
| P3 | Yaml を書かない担当者 | P1 から受け取った Yaml を Web UI に貼って実行する | スペース管理者 |

> **全ペルソナがスペース管理者である必要がある。** ステータスの追加・更新・削除 API が
> スペース管理者権限を要求するため（[API 制約](../research/backlog-api-constraints.md#権限)）。
> これは「一般メンバーがセルフサービスでプロジェクトを立ち上げる」用途を最初から諦める決定である。

## 5. ユースケース

### UC-1 新規プロジェクトを Yaml から作成する（主シナリオ）

1. P2 が標準 Yaml をコピーし、プロジェクトキーと名前を変える
2. `blueprint plan -f projects/PROJ_A.yaml` で計画を確認する
3. `blueprint apply -f projects/PROJ_A.yaml` を実行する
4. プロジェクトが作成され、課題種別・ステータス・カテゴリー等が定義通りになっている

### UC-2 まだ課題が1件も無い既存プロジェクトに適用する

GUI で作ってしまったプロジェクトを Yaml 管理に乗せ換える導線。
初期状態の課題種別・ステータスをクリーンアップしてから定義通りにする。
**課題が1件でも存在する場合は実行不可**（検証段階で中断）。

### UC-3 適用せずに計画だけ見る（dry-run）

`blueprint plan` は Backlog を一切変更せず、実行したら何が起きるかだけを出す。
`--output json` で機械可読な計画を出し、利用者側で PR コメント等に組み込める。

### UC-4 Web UI から実行する

static hosting された SPA に Yaml を貼り、API キーを入力して plan → apply。
Backlog API が CORS に対応しているため、サーバを持たずにブラウザから直接叩ける。

### UC-5 CI から実行する

`npx` で CLI を呼ぶ。終了コードで成否を判定する。専用の GitHub Action は提供しない。

### UC-6 既存プロジェクトを雛形の出発点として書き出す

UC-1 の「標準 Yaml をコピーする」の、その標準 Yaml を作る導線。

1. P1 が、よくできているプロジェクトを `blueprint export PROJ_A > projects/standard.yaml` で書き出す
2. Webhook の URL は `${WEBHOOK_URL_1}` に置き換わっているので、値を環境変数に用意する
3. `key` と `name` を新しいプロジェクトのものに書き換える
4. UC-1 に入る

**書き出し元のプロジェクトは課題を持っていてよい**（[EX-3](../design/export.md#ex-3-プロジェクトの存在は要求するが課題の有無は見ない)）。
`export` は読み取りしか行わないので、稼働中のプロジェクトを雛形の元にできる。
書き出したものを**同じプロジェクトに**適用しようとすれば、これまでどおり V-B3 が止める。

## 6. スコープ

### 管理対象リソース

| 分類 | リソース |
| --- | --- |
| コア | プロジェクト基本設定、課題種別、カテゴリー、マイルストーン（版）、ステータス |
| カスタム属性 | カスタムフィールド（8種）とその適用課題種別 |
| メンバー・権限 | プロジェクト参加チーム、プロジェクト参加ユーザー、プロジェクト管理者 |
| 通知 | Webhook |

同じリソース群を逆向きに読み、既存プロジェクトをマニフェストとして書き出す
（`export`。UC-6 / [設計](../design/export.md)）。書き出しは読み取りしか行わない。

### 非スコープ（やらないと決めたこと）

| 対象 | 理由 |
| --- | --- |
| 差分取り込み・継続的な同期 | 依頼者の明示的な除外。プロジェクト作成時点だけを考える |
| state ファイル（Terraform の tfstate 相当） | 差分管理しないので不要。Backlog の現状を毎回読んで計画を立てる |
| 課題が存在するプロジェクトへの適用 | 破壊的操作の影響範囲が読めない。検証で弾く |
| **`export` を使ったドリフト検出・継続同期** | `export` が書き出すのは雛形の出発点であって、ツールは2つのマニフェストを比較しない。利用者が CI で diff を取る運用は妨げないが、ずれの監視・報告・修正はいずれも約束しない（[EX-19](../design/export.md#ex-19-ドリフト検出の道具ではない)） |
| GUI フォームによる Yaml 生成 | 初期スコープ外。Web UI は貼り付け実行のみ |
| Git リポジトリ（1プロジェクトに複数作れる） | **API に作成・更新・削除が無い**（参照と PR 操作のみ）。書けるようにすると「Yaml に書いたのに作られない」キーが生まれ、ツールの約束が壊れる。詳細は下記 |
| 課題・Wiki などのコンテンツ | 設定ではなくデータ。管理対象が際限なく広がる |
| スペース設定・優先度・完了理由 | API で変更できない。優先度と完了理由はスペース固定値 |
| プロジェクトの削除・アーカイブ | 誤爆の被害が大きすぎる。人間が GUI でやるべき操作 |

### Git リポジトリを非スコープにした判断

Backlog は1プロジェクトに複数の Git リポジトリを持てるため、
マニフェストで宣言したくなる対象ではある。しかし API は参照しかできない。

「存在確認だけする（作らないが、無ければ警告する）」という案も検討したが採らない。
マニフェストに**「作るもの」と「確認するだけのもの」という2つの意味が混ざる**のが理由。
`statuses` や `issueTypes` と同じ見た目で並んでいるのに挙動だけが違うキーは、
利用者が「これも作られる」と読み違える。

また「現状を確認する」機能は、差分適用を非スコープにしている本ツールの仕事ではない。

Git まわりで**スコープ内に残るもの**。

| 項目 | 内容 |
| --- | --- |
| `settings.useGit` / `settings.useSubversion` | Git / Subversion 機能の有効化。プロジェクト作成 API で指定できる |
| Webhook の Git 関連イベント | `Git Pushed` / `Git Repository Created` |

「Git を使えるプロジェクトを作り、push 時に通知を飛ばす」ところまでは宣言できる。
空のリポジトリを置く操作だけが手作業で残る。

## 7. 設計を縛る前提

1. **Backlog API でできることしかやらない。** GUI にしかない設定は管理対象にしない
2. **トランザクションが無い。** 途中で失敗したら中途半端な状態が残る前提で設計する
3. **更新系 API は直列・1秒間隔が公式推奨。** 並列化による高速化は選択肢にない
4. **削除には必ず振替先が必要。** 課題種別・ステータスの削除 API は代替 ID が必須パラメータ
5. **既定ステータス4つは削除できない。** クリーンアップで消せない要素が構造的に存在する
6. **表示順を変更できるのはステータスだけ。** 他は作成順で決まり、後から並べ替える手段が無い
7. **リクエスト数がそのまま所要時間になる。** マニフェストの書き方が実行速度を左右する

## 8. 中核となる要求

依頼者から明示された、譲れない要求。

| ID | 要求 |
| --- | --- |
| R-1 | 初期状態から存在するもの（ステータス・課題種別）はクリーンアップしてから定義通りにする |
| R-2 | 消せないもの・0件にできないものが定義上0件になるなら、**最初の検証で指摘して中断する**。実行を始めてから気付くのは許容しない |
| R-3 | dry-run を用意する |
| R-4 | 課題が1件でも存在するプロジェクトは実行不可にして良い |
| R-5 | 実行者がスペース管理者でなければ実行させない |
| R-6 | CLI（ローカル・CI）と Web UI（static hosting）の両方から実行できる |

R-2 が設計上いちばん重い。「実行してみないと分からない」ことを可能な限り検証段階に前倒しする
必要があり、これが検証仕様の厚みとして [要件定義](requirements-definition.md#5-検証仕様) に現れる。
