# export の設計

最終更新: 2026-09-23
前提: [要求設計 §6](../requirements/requirement-design.md#6-スコープ) / [要件定義 FR-8](../requirements/requirements-definition.md#fr-8-export) / [core のデータモデル](core-reconciler.md) / [マニフェストのスキーマ定義](manifest-schema.md)

既存の Backlog プロジェクトを読み、マニフェストとして書き出す `export` の設計。

## 0. なぜスコープ外だった決定を覆すのか

`export` は当初 **非スコープ**だった。[要求設計 §6](../requirements/requirement-design.md#6-スコープ) の
非スコープ表に「既存プロジェクトからの Yaml 逆生成（export）／初期スコープ外。将来の候補」とあり、
[要件定義 FR-7](../requirements/requirements-definition.md#fr-7-web-ui) の末尾と README の
"What it is not" も同じことを言っていた。

**挙げられていた理由は「初期スコープ外」だけで、技術的な不可能性はどこにも無い。**
3箇所を読み直しても、それ以上のことは書かれていない。優先順位の表明であって、
設計上の障害の記録ではなかった。

思想として `export` に触れうる記述は1つだけある。同じ §6 の「Git リポジトリを非スコープにした判断」が
*「『現状を確認する』機能は、差分適用を非スコープにしている本ツールの仕事ではない」*と書いている。
ただしその文脈は「マニフェストに『作るもの』と『確認するだけのもの』を混ぜない」ことであり、
**読み取り専用のコマンドを別に持つことを否定してはいない。**

一方で、覆すだけの理由が揃っている。

| 根拠 | 内容 |
| --- | --- |
| [要求設計 §3](../requirements/requirement-design.md#3-提供する価値) | 提供する価値の筆頭が「雛形の配布」。`export` は雛形の作り方を1つ増やす |
| [UC-1](../requirements/requirement-design.md#uc-1-新規プロジェクトを-yaml-から作成する主シナリオ) | 主シナリオが「標準 Yaml をコピーし、名前とキーを変える」。その標準 Yaml を手で書き起こす作業が消える |
| 非スコープとの整合 | `export` は state ファイルを持たず、差分適用もしない。既存の「現状を毎回読む」経路（`read()`）をそのまま使う |
| 実装の土台 | 各 reconciler の `read()` が返すスナップショットは、既にマニフェストのキーとほぼ1対1である |

**残る懸念は `export` そのものではなく、その使われ方にある。** `export` があると、利用者が
「CI で export して、リポジトリの Yaml と diff する」というドリフト検出のループを**自分で**組める。
ツールは何もしないが、README の "It keeps no state ... no drift detection" という約束は
「ツールはやらないが材料は出す」に変わる。これは `export` を入れない理由ではなく、
**入れたうえで `export` が何でないかを明示する理由**である（EX-19）。

## 1. 責務の分割

### EX-1: `read` → `toManifest` → `serializeManifest` の3段にする

| 決定 | 内容 |
| --- | --- |
| EX-1 | `export` は既存 reconciler の `read()` をそのまま再利用し、`toManifest(snapshots): ManifestInput`（純粋関数）と `serializeManifest(manifest, version): string` に分ける。**`Reconciler` に `export()` を生やさない。** 写像とシリアライズはどちらも `packages/core` に置く |

```
Backlog ──[ 既存の read() ]──▶ ResourceSnapshots ──[ toManifest ]──▶ ManifestInput ──[ serializeManifest ]──▶ Yaml
             GET のみ                                   純粋関数                            純粋関数
```

`plan` の分解（[C-1](core-reconciler.md#c-1-reconciler-は-read-と-plan-だけを持ちapply-は持たない) /
[C-2](core-reconciler.md#c-2-plan-は純粋関数ネットワークにアクセスしない)）と同じ形である。

- **`Reconciler` に `export()` を足さない理由。** 要件定義 NFR-8 が約束しているのは
  「リソースを1つ増やす作業がファイルを1つ足して適用順序に並べるだけで済む」こと。
  インターフェースに1つメソッドが増えるたび、その作業に1項目ずつ増える。
  そして `export()` が必要とする情報は `read()` が返すスナップショットに全部入っている。
- **純粋関数にする理由。** C-2 と同じ。固定スナップショットに対して全パターンを検証でき、
  往復（EX-18）を実 API 無しで確かめられる。
- **core に置く理由。** NFR-6。`apps/cli` に写像を書くと、Web UI に載せるときに二重実装になる
  （EX-20 / [FR-7](../requirements/requirements-definition.md#fr-7-web-ui)）。

**採らなかった案: `read()` とは別に `export` 専用の取得を書く。** GET の一覧が2箇所に分かれ、
片方にリソースを足し忘れると `export` だけが黙って項目を落とす。

## 2. 対象と権限

### EX-2: 実行者の権限は問わない

| 決定 | 内容 |
| --- | --- |
| EX-2 | `export` も S5（V-B1）を走らせるが、スペース管理者であることは求めない。読めない GET があれば、その取得の失敗として中断する |

当初は「スペース管理者でなければ中断する」だった。要求 R-5 がコマンドで限定していなかったためである。
R-5 と [FR-5.4](../requirements/requirements-definition.md#fr-5-認証と権限) を撤回したので、`export` だけ残す理由が無い。

**プロジェクト管理者が自分のプロジェクトを雛形にできる。** 当初の案で失うとしていたものがこれだった。
一方で、`export` が叩く GET には Webhook 一覧のようにプロジェクト管理者以上を要する
（[API 制約](../research/backlog-api-constraints.md#webhook)）ものが混ざるので、
プロジェクト管理者でもない一般メンバーは途中で落ちる。落ちる前に権限で止める表は持たない
（FR-5.4 の撤回理由と同じ）。

### EX-3: プロジェクトの存在は要求するが、課題の有無は見ない

| 決定 | 内容 |
| --- | --- |
| EX-3 | 対象プロジェクトが存在しなければエラー（404 を情報として扱わない）。**課題件数によるゲート（V-B3 相当）は置かない。** 課題件数は読み取り、stderr の情報として出す |

[AGENTS.md](../../../AGENTS.md) の「Do not widen the target」と
[検証パイプライン §7](validation-pipeline.md#7-適用対象の限定) が守っているのは**書き込み先**の限定である。
§7 が列挙する被害（「Yaml に名前が無い参加者が全員削除される」）はすべて適用の被害で、
`export` は `Action` を1件も作らない。

ゲートを置くと正当な用途が消える。**稼働している良いプロジェクトを雛形にする**のは
UC-1 の「標準 Yaml をコピー」の供給源としてもっとも自然で、
課題0件のプロジェクトからしか書き出せないなら、雛形にできるプロジェクトが実質存在しない。

危険な経路は既に塞がっている。稼働中のプロジェクト P から書き出したマニフェストを
そのまま P に `apply` しようとすれば V-B3 が止める（AC-4）。書き出した `key` は P を指すので、
UC-1 に使うには利用者が `key` と `name` を書き換える必要があり、それは既存の運用と同じ手順である。

**VP-5（課題件数を確認できなければ止める）を `export` に持ち込まない。** VP-5 は
破壊的操作を止める唯一のゲートを開いたままにしないための決定である。`export` にゲートは無く、
課題件数は案内のために読むだけなので、取得に失敗したときは他の GET の失敗と同じく
「読めなかった」として中断する（EX-17 が半端な出力を防ぐ）。

**`<key>` には S3 の `key` の規則（V-A3）をそのまま当てる。** `createExport` が S5 の前に判定し、
合わなければ GET を1回も飛ばさずに止まる。診断の `id` は `V-A3` を借り、`stage` も `"schema"` にする。
EX-9a が V-A5 を借りなかったのは直す場所と `hint` が違うためだが、ここは規則も直し方も同じで、
違うのは「ファイルに書いたか、引数に書いたか」だけである。同じ誤りに2つの ID を振ると、
ID が「誤りとその直し方を1対1で結ぶ」役目を果たさない。

判定を CLI に置かないのは、`projectKey` が `createExport` の組み立てる URL のパスに入る値だからである。
**「不正なキーで GET を飛ばさない」は、GET を発行するモジュールの中でしか守れない。**
CLI に置くと Web UI に載せたとき（EX-20）に同じ検査をもう一度書くことになり、NFR-6 が禁じる形になる。

実装の形としては、課題件数の取得は**失敗を捕まえずにそのまま投げる**。
`readSpaceSnapshot` が同じ取得を捕まえて V-B3 の診断に変えているのは VP-5 のためであり、
その文言（`project already has issues` の系統）を `export` が借りると、
読めなかっただけの状況に「ゲートで止めた」という意味が付く。

## 3. Webhook URL の書き出し

### EX-4: `hookUrl` を取得値のまま書く

| 決定 | 内容 |
| --- | --- |
| EX-4 | `webhooks[].hookUrl` は GET で取得した値をマニフェストに書く。`${ENV}` に置き換えるかは利用者が決める（E-8） |

`export` は Backlog の設定をマニフェストに写す。
Webhook URL を自動的に `${ENV}` に置き換えると、書き出したファイルだけでは同じ設定を再現できない。
変数展開は環境ごとに変わる値を差し込む手段であり、どのフィールドに使うかは利用者が決める。

### EX-5: `${` を `$${` にエスケープする

| 決定 | 内容 |
| --- | --- |
| EX-5 | 書き出すすべての文字列値で `${` を `$${` に置き換える（[E-3](manifest-schema.md#3-env-展開) の逆写像） |

Backlog 側の値に `${NAME}` がリテラルで含まれていることは十分ありうる。
E-3 が `$${NAME}` というエスケープを用意したのは、まさに課題テンプレート
（`templateDescription`）にプレースホルダを書く実例を想定してのことである。

エスケープしないと、書き出したマニフェストを読み戻したときに S2 がそれを展開しようとし、
**V-A4（`${ENV}` が解決できない）で往復が壊れる**。

**`${` を無条件に置き換えてはならない。** S2 が展開するのは完全な参照だけなので、
`${foo`（閉じ括弧が無い）や `${}`（空）まで置き換えると、読み戻したときに
S2 がそれらを参照と見なさず `$` が1つ増えたまま残る。**S2 と同じ正規表現で参照を見つけ、
`$` を1つ前置する**こと。エスケープと展開が同じパターンを見ていれば、
「見つけて `$` を足せば、S2 は必ず `$` を1つ剥がす」という関係が正規表現1つで保たれる。

**EX-5 が実際に効くのは同定名以外の値**（プロジェクト名・`templateSummary` /
`templateDescription`・`description`・`unit`・`items`）である。同定名に `${NAME}` が
含まれていれば、それは `}` を含むので EX-9b で先に止まる。エスケープの有無で
名前の扱いが変わることはない。

## 4. 写像

### EX-6: 書き出さないもの

| 決定 | 内容 |
| --- | --- |
| EX-6 | `oldname`、`archived`、スキーマに無い応答項目（`displayOrder` など）は書き出さない。**`export` は完全な写像ではない** |

- **`oldname`**: マニフェスト側にしかない概念であり、スナップショットからは復元できない。
  そもそも書き出すべきものが存在しない。`oldname` は移行元のヒントであって
  「あるべき姿」ではなく（[要件定義 §2.3](../requirements/requirements-definition.md#23-同定キーを-name-にすることの帰結)）、
  スナップショットは既にあるべき姿だからである。
  差分ゼロは壊れない。[§6.2](core-reconciler.md#62-oldname-の解釈) の1行目が
  「`name` と同名のリソースが存在すれば `oldname` は無視する」と定めている。
- **`archived`**: マイルストーンにもプロジェクトにも存在するが、スキーマに無い。
  雛形を新規プロジェクトに当てれば、すべて未アーカイブとして作られる。
  アーカイブ済みプロジェクトの `export` は**許す**。読み取りに支障が無く、
  「雛形の出発点」としての価値も変わらない。
- **`displayOrder`**: 表示順は配列の並び順として表現されるので、実質は落ちない。

### EX-7: `statuses`

| 決定 | 内容 |
| --- | --- |
| EX-7 | 応答が返した順にそのまま並べる。ID 1〜4 は `name` だけ、それ以外は `name` と `color` を書く |

既定ステータスに `color` を書けないのは V-A6a、カスタムに `color` が要るのは V-A26。
`GET /projects/:key/statuses` は表示順で返すので、その順に書けば
[`orderAfterApply`](core-reconciler.md#24-表示順の扱い) の予測と一致し、`reorder` は `noop` になる。

既定かどうかは ID で判定する（[K-5](manifest-schema.md#k-5-既定ステータスの判定を-json-schema-でやらない)）ので、
スペースの言語設定が何であっても正しく動く。

### EX-8: `access`

| 決定 | 内容 |
| --- | --- |
| EX-8 | `teams` = `GET /projects/:key/teams`、`administrators` = `GET /projects/:key/administrators`、`members` = `GET /projects/:key/users?excludeGroupMembers=true` から `administrators` を除いたもの。いずれも応答の順。**チーム経由でも参加している個人参加者は `members` に残す**。`teams` はチーム ID で書き（A-6）、各要素の行末にチーム名を、`members` / `administrators` はユーザー ID（数値）で書き（A-7）、各要素の行末には表示名をコメントで付ける（EX-16 の例外）。表示名が空ならコメントを付けない |

[§6.3](core-reconciler.md#63-access-の差分算出) が「個人参加のあるべき集合 = `members` ∪ `administrators`」と
定めているので、`administrators` を `members` から除いた形が最小の書き方になり、
読み戻せば同じ集合に戻る。

**チーム経由でも個人参加している人を `members` から落とさない。** 落とすと、
読み戻した計画がその人の個人参加を `delete` する Action を出す。
残すと V-A16（チーム経由の重複記述）の警告が出るが、警告は適用を止めない。

> **`export` は「差分ゼロ」を「警告ゼロ」より優先する。** 両立しないのはここだけである。
> 警告は「リクエストが1件増える」ことを教えるものであり（[V-A16](../requirements/requirements-definition.md#51-静的検証マニフェストだけで判定できるもの)）、
> 削られるのは利用者が中身を見て判断すべき行である。ツールが黙って落とすと計画が変わる。

`administrators` にスペース管理者は現れない。A-5 / V-B11 が示すとおり、
スペース管理者はそもそもプロジェクト管理者になれないので、
書き出したマニフェストが V-B11 で落ちることはない。

### EX-10: `settings` は14キーに射影する

| 決定 | 内容 |
| --- | --- |
| EX-10 | 応答を [スキーマ定義 §5](manifest-schema.md#5-settings) の14キーに射影する。応答に無いキーは書かない。1つも残らなければ `settings` キーごと省く |

`ProjectSnapshot.settings` は応答のスカラー値を**全部**持つ（`projectKey` や `archived` も入る）ので、
そのまま書き出すと V-A1（未知キー）に当たる。射影は必須である。

値の型が合わないもの（真偽値のはずが文字列など）や enum の外にある
`textFormattingRule` は EX-9c で止める。

> **`要検証`** — `GET /api/v2/projects/:key` の応答が §5 の14キーをすべて含むかは実測していない。
> 公式リファレンスの応答例には `grandchildIssueEnabled` / `useDocument` / `useGit` /
> `useSubversion` が無い。応答に無いキーは `export` に現れず、その雛形を新規プロジェクトに
> 当てたときは Backlog の既定値になる（[K-3](manifest-schema.md#k-3-省略されたスカラーキーは現状維持)）。
> **返るキーの数が何であっても、書き出したマニフェストを同じプロジェクトに `plan` した結果は
> 差分なしになる。** 実測できたら、含まれないキーを `docs/manifest.md` に列挙する。

### EX-11: `customFields` は型ごとの許可キーに射影する

| 決定 | 内容 |
| --- | --- |
| EX-11 | `type` ごとに「その型が持てるキー」へ射影する。表は [スキーマ定義 §9](manifest-schema.md#9-customfields) の条件表と**同じ出どころ**から導く。`typeId` / `initialValueType` は `CUSTOM_FIELD_TYPE_IDS` / `INITIAL_VALUE_TYPE_IDS` の逆引き。`applicableIssueTypes` が空ならキーを省く。許可キーの値は `false` / `0` / `""` でも書く |

許可される型固有キー（共通キー `name` / `type` / `description` / `required` /
`applicableIssueTypes` は全型）。

| `type` | 型固有キー |
| --- | --- |
| `text` / `textArea` | 無し |
| `number` | `min` `max` `initialValue` `unit` |
| `date` | `min` `max` `initialDate` `initialValueType` `initialShift` |
| `singleList` / `multipleList` / `checkBox` / `radio` | `items` `allowInput` `allowAddItem` |

`date` はさらに `initialValueType` で絞る。`specifiedDate` なら `initialShift` を落とし、
`todayPlusShift` なら `initialDate` を落とし、`today` と未指定なら両方落とす（§9 の条件表）。

**射影表をこの文書とコードで二重に持たない。** [M-1](manifest-schema.md#m-1-json-schema-は手書きせずコード側のスキーマ定義から生成する) が
「手書きの JSON Schema と実行時バリデータを二重に持つと必ずズレる」として退けたのと同じ形である。
`CUSTOM_FIELD_CONDITIONS` が持つ禁止キーの補集合として、コード上は1つの定数から導く。

`applicableIssueTypes` の空配列でキーを省けるのは、配列キーの省略が空配列と同義
（[K-1](manifest-schema.md#k-1-配列キーの省略は空配列であって管理対象外ではない)）で、
空が「絞らない＝全種別」を意味するため。reconciler 側も空のときは比較対象にしないので
差分は出ない。

> **`要検証`** — `GET /api/v2/projects/:key/customFields` が型固有キーを他の型で
> どう返すか（欠落・`null`・`false` / `0`）は実測していない。`null` は `optionalString` などが落とし、
> `false` / `0` は射影が落とすので、**どの返り方でも S3 の `if`/`then` を通る。**
> 実測結果で仕様は変わらない。実測できたら research 文書に応答の形を記録する。

### EX-12: `webhooks[].events`

| 決定 | 内容 |
| --- | --- |
| EX-12 | `allEvent` が真なら `all`。そうでなければ `activityTypeIds` を昇順に並べ、`WEBHOOK_EVENTS` で名前を引けるものは名前、引けないものは数値のまま書く。0件は EX-9f で止める |

W-1（名前と数値の両方を受け付ける）/ W-2（`all` は `allEvent: true`）のとおり。
[§6.4](core-reconciler.md#64-webhooks-の差分算出) の比較は順序を無視した集合なので並びは自由だが、
**出力を安定させるため昇順に固定する**。同じプロジェクトを2回書き出したら同じ文字列になる、
という性質は diff を取る利用者にとって前提である。

名前を引けない ID は数値で書く（W-1 の前方互換）。読み戻すと V-A24 の警告が出るが、
それは Backlog が新しいイベントを追加したという正しい情報である。

> **`要検証`** — イベントを1つも選ばない Webhook を Backlog が保持しうるかは実測していない。
> 保持しうるなら EX-9f が出る。保持しえないなら EX-9f は到達しない枝として残る
> （`numbers()` は応答の欠落を `[]` に寄せるので、型の上では常に起こりうる）。

### EX-13: 日付は先頭10文字

| 決定 | 内容 |
| --- | --- |
| EX-13 | `startDate` / `releaseDueDate` / 日付型の `min` / `max` / `initialDate` は応答の先頭10文字を取る |

`read()` の `asDate` / `asRange` と同じ扱い。時刻は常に `T00:00:00Z` なので
タイムゾーンのずれは起きない（[実装中に見つかった事項 #1](../research/backlog-api-constraints.md#実装中に見つかった事項実測で確定)）。

### EX-9: マニフェストとして表現できない実状は、全件列挙して失敗する

| 決定 | 内容 |
| --- | --- |
| EX-9 | Backlog 側の実状がマニフェストとして表現できないとき、診断を**全件**列挙して終了コード 1 で失敗し、**何も書き出さない**。診断の `id` は EX-9a〜EX-9h、`stage` は `"snapshot"` |

書き出して `validate` に落とさせる案を採らない。**`export` が吐いたものが同じツールの
`validate` で落ちる**という自己矛盾を利用者に見せることになる。
警告を出して書き出す案も採らない。そのファイルは `plan` に通らないので雛形として使えず、
警告を見落とした人がリポジトリにコミットする。接尾辞を付けて改名するような案は、
`export` の約束（いまの実状を書く）を破って「あるべき姿」をツールが捏造することになる。

全件列挙するのは VG-1 と同じ理由。1件直すたびに次が出るループを作らない。

**既存の V-A* を借りない。** たとえば V-A5（同一配列内の `name` 重複）は
「マニフェストに重複を書いた」という**利用者がファイルで直せる誤り**を指し、
`hint` は「片方を改名せよ」になる。`export` の場合に直す場所は Backlog 側であり、
同じ ID に2つの `hint` が付くことになる。ID は診断とその直し方を1対1で結ぶものなので分ける。

**`export` 専用の診断 ID 体系も作らない。** `Y-5`（複数ドキュメント）が既に
「設計文書の決定 ID をそのまま `Diagnostic.id` に使う」前例で、
[README の採番規則](../README.md#決定-id-の採番)がそれを許している。
決定と診断が同じ ID なら、エラーメッセージからこの文書へ直接たどり着ける。

`stage` を `"snapshot"` にするのは、判定の根拠がスペースから読んだ実状であり、
S6 の定義そのものだから。位置情報を持たない点も DG-5 と一致する。

`path` は**書き出されるはずだった位置**（`webhooks/2/name`）を指し、
その添字は**スナップショット上の位置**、つまり Backlog が返した n 件目である。
EX-9d / EX-9e が要素を落とすと出力側の添字はこれとずれるが、
**利用者が直すのは Backlog の n 件目**なので、指すべきはスナップショット側になる。

| ID | 対象 | 判定 |
| --- | --- | --- |
| EX-9a | 同一リソース種別内の `name` の重複 | Backlog は重複を許すが、同定キーが `name` である以上マニフェストには書けない。**同名の2件目以降の各位置に1件ずつ出す。** `path` は1つの位置しか指せないので、1件の診断で2件を語らない |
| EX-9b | `name` に `}` を含む | V-A22。`{$ref:<kind>:<name>}` の記法が名前の終端を `}` で判断する。**`access` の要素（チーム ID・ユーザー ID）は対象外。** これらは名前ではなく数値で書かれ（A-6 / A-7）、そのまま `request.params` に載るので、`{$ref:...}` の文字列には埋め込まれない（V-A22 と同じ線引き） |
| EX-9c | enum の外にある値（課題種別・ステータスの `color`、`settings.textFormattingRule`、型の合わない `settings` の値） | K-4 / V-A8 / §5 |
| EX-9d | 名前を持たない `typeId` / `initialValueType` | K-6 が数値を受け付けないので表現できない |
| EX-9e | 名前を引けない `applicableIssueTypes` の ID | V-A10 を通らない。数値をそのまま書くより止めるほうがよい |
| EX-9f | イベントを1つも持たない Webhook | スキーマが `minItems: 1` を課す |
| EX-9g | 選択肢を1つも持たないリスト型のカスタム属性 | 同上 |
| EX-9h | 上記以外で、組み上げたマニフェストが S3 / S4 を通らない値（日付型と数値型で取り違えた `min` / `max`、`^\d{4}-\d{2}-\d{2}$` に合わない日付、`startDate` > `releaseDueDate`、`min` > `max` など） | **受け皿。** 個別に列挙しない（下記） |

### EX-9h を個別の検査にしない

EX-9a〜EX-9g は「Backlog 側でどう直すか」を言える固有の `hint` を持つので個別に置く。
一方、**マニフェストとして表現できない実状は他にもあり、その一覧はスキーマと静的検証が既に持っている。**
1つずつ枝番を切ると、スキーマにキーが増えるたびに `export` 側の検査を書き足すことになり、
[M-1](manifest-schema.md#m-1-json-schema-は手書きせずコード側のスキーマ定義から生成する) が
退けた二重管理そのものになる。

そこで **`toManifest` は組み上げたマニフェストに S3（スキーマ）と S4（静的意味）を
そのまま当て、残った誤りを EX-9h に写す**。`plan` が使うのと同じバリデータなので、
スキーマが変わっても `export` の網は自動で追随する。

| 規則 | 内容 |
| --- | --- |
| 警告は捨てる | `export` は警告を出さない（CL-8）。V-A24（未知の activityTypeId）は EX-12 が意図して通している |
| 同じ `path` に EX-9a〜EX-9g が既にあれば捨てる | EX-9c と S3 の `enum`、EX-9f / EX-9g と `minItems`、EX-9a と V-A5、EX-9b と V-A22 は同じ誤りを指す。固有の `hint` を持つほうを残す |
| 位置情報は持たない | DG-5。マニフェストはファイルから読んだものではない |

これにより **`toManifest` は「返したマニフェストは S1〜S4 を通る」という性質を自分で保証する。**
`validateSchema` も `validateStaticSemantics` も入力だけの関数なので、EX-1 の純粋性は保たれる。

EX-9h は [V-A21](validation-pipeline.md#s3-スキーマ) が S3 の受け皿であるのと同じ位置づけである。
**頻出するなら固有の枝番を切る合図**になる。

メッセージは英語（NFR-9）。利用者が Backlog 上で付けた名前はそのまま埋める（DG-1）。

```
2 export errors. Nothing has been written.

ERROR [EX-9a] webhooks/2/name: another webhook is already named "Slack 通知"
  → resources are matched by name, so a manifest cannot hold both.
    rename one of them in Backlog, then export again

ERROR [EX-9c] issueTypes/1/color: the issue type "バグ" has the color "#123456",
  which is not one of the ten colors this tool accepts
  → choose one of the ten colors for it in Backlog, then export again
```

`hint` の末尾にピリオドを置かないのは既存の V-A* に揃えるためである
（文中の区切りには `. ` を使う）。

集計行は既存の `N validation errors. Nothing has been applied.` と同じ形で、
名詞と末尾の文だけを差し替える。

## 5. 出力

### EX-14: 配列キーは0件でも書く。`settings` だけは空なら省く

| 決定 | 内容 |
| --- | --- |
| EX-14 | `issueTypes` / `statuses` / `categories` / `milestones` / `customFields` / `webhooks` は0件でも `[]` を書く。`access` は3キーとも常に書く。`settings` は空なら省く |

K-1 により `[]` と省略は同じ意味だが、**雛形の読み手にとっては別**である。
`categories: []` は「このプロジェクトにカテゴリーは無い」を伝え、
キーが無いのは「書き忘れたのかもしれない」を残す。`export` の出力は
利用者がこれから編集する土台なので、キーが並んでいるほうが編集の起点になる。

`settings` だけ扱いが違うのは K-3 のため。スカラーキーの省略は「現状維持」であり、
`settings: {}` は何も言っていない。書いても読み手に情報が増えない。

**空の `settings` を省くのは `serializeManifest` の側である。** `toManifest` は空でも
常に `settings` を載せる。写像が答えるのは「マニフェストが何を言うか」で、
省略するかどうかは「どう見えるか」の判断だからである。K-3 のもとで `{}` と省略は
同じことを言うので、データの側に体裁の判断を置く理由がない。
両方に置くと EX-14 が2箇所に実装される。

### EX-15: `$schema` はコメント行だけを書く

| 決定 | 内容 |
| --- | --- |
| EX-15 | 先頭行に `# yaml-language-server: $schema=https://simochee.github.io/backlog-blueprint/schema/<version>/project.json` を出す。`<version>` は実行中のツールの版。**`$schema:` キーは書かない** |

D-1 / D-2 のとおり、スキーマは版付き URL で配布され、版は CLI の semver と一致する。
[M-2](manifest-schema.md#m-2-schema-キーを受理して無視する) が `$schema` キーを
「受理して**無視する**」と決めている以上、**無視される値を生成物に入れる理由が無い**。
正としているのはコメント形式のほうである。

**配布 URL の組み立ては core が唯一の出どころになる。** 同じ URL は
`packages/schema` が `$id` に入れるものと同じで（要件定義 §7.1）、版がずれれば
「エディタが引く URL」と「実際に配布される URL」が食い違う。`packages/schema` は
core に依存しているので逆向きの import はできず、core が持つしかない。
`export` の関心事ではないので `export/` の下には置かない。

### EX-16: 先頭行以外にコメントを出さない

| 決定 | 内容 |
| --- | --- |
| EX-16 | 生成物にコメントを書かない（EX-15 の1行と、EX-8 の `access` の各要素に付ける名前を除く） |

`yaml` パッケージはコメント付きで出力できるが、生成物に説明を埋め込むと
**再度書き出したときに失われ、手で足したコメントも消える**。
キーの意味はスキーマの `description` がエディタのホバーで言い、振る舞いは
`docs/manifest.md` が説明し、実行時の注意は stderr の案内（CL-8）が担う。
同じ説明を4つ目の場所に置かない。

**`access` の名前のコメントはこの理由に当たらない。** 説明ではなく書き出す時点のデータであり、
書き出すたびにスペースから引き直されるので、再度書き出しても失われない。
これが無いと、A-6 でチームを ID で書くことにしたマニフェストが人に読めなくなる。

### EX-17: 全部成功したときだけ、完成した Yaml を1回で書く

| 決定 | 内容 |
| --- | --- |
| EX-17 | 読み取りと写像がすべて成功したときだけ stdout に書く。失敗したときは stdout に1バイトも出さない |

`backlog-blueprint export PROJ_A > projects/PROJ_A.yaml` が想定される使い方である以上、
**途中で失敗したときに半端なファイルが残る経路を作らない。**
リソースごとに書き進める実装は、読みやすさの点でも利がない。

### 出力の形

| 項目 | 決定 | 理由 |
| --- | --- | --- |
| トップレベルのキー順 | [スキーマ定義 §4](manifest-schema.md#4-トップレベル) の順（`key` → `name` → `settings` → `issueTypes` → `statuses` → `categories` → `milestones` → `customFields` → `access` → `webhooks`） | 文書とスキーマと生成物で並びが同じなら、3つを見比べられる |
| 配列要素のキー順 | `name` を必ず先頭に置き、以下は各スキーマの表の順 | 読み手が要素を名前で追える |
| インデント | 2スペース。配列の `-` は親キーより1段下げる | `manifest-example.yaml` と README の見え方に揃える |
| 行の折り返し | しない | 折り返しは意味を変えないが diff を汚す。折り畳みスカラーは空白の再構成を挟む |
| 複数行文字列 | リテラルブロック（`\|` / `\|-`）。末尾改行の有無は値のとおり | 末尾改行は値の一部である |
| 引用符 | 必要なときだけ二重引用符。パーサと**同じ設定**（YAML 1.2 / core schema）でシリアライズする | `#` で始まる色、`true` / `null` / `123` / `~` のように素で書くと文字列に戻らない値を、ライブラリの側に判定させる |
| アンカー・エイリアス | 出さない | Y-4 は読む側の話。生成物にアンカーが出る理由を読み手に説明できない |
| 末尾 | 改行1つで終える | |

**引用符を自前で判定しない。** `*` で始まるユーザー ID（`*oNejJk6xEn`）と `#` で始まる色は
このプロジェクトが実際に踏んだ罠だが（V-A23 / [反面教師 §3.2](syntax-reference-github.md#32--始まりの色は引用符が要る)）、
`yaml` のシリアライザにパーサと同じ設定を渡せば、その判定はライブラリが持つ。
自前の規則を書くと、パーサ側の設定が変わったときに追随しない規則が1つ残る。
**保証はテスト（EX-18 の (2)）が読み戻して行う。**

## 6. 往復

### EX-18: 受け入れは3層で書く

| 決定 | 内容 |
| --- | --- |
| EX-18 | (1) `toManifest` の出力から計画を組むと全 Action が `noop`（固定スナップショット）。(2) `export` の stdout を `plan` に食わせて終了コード 0 と `No changes.`（`mockBacklog`）。(3) 課題を持つプロジェクトでも `export` は成功し、その出力の `plan` は V-B3 で止まる。加えて UC-1 の往復 |

**(1) だけでは足りない。** 純粋関数のレベルでは、値が Yaml の文字列になってから
読み戻すまでの間に起きることが捕まらない。

- 色の引用符（`"#ea2c00"`）
- Yaml が非文字列に読む名前（`123` / `true` / `null` / `~`）
- `templateDescription` の末尾改行（`|` と `|-` の差）
- EX-5 の `$${` エスケープ

**(2) はそれを文字列経由で確かめる。** `mockBacklog` でプロジェクトを組み、
`export` の stdout をそのまま `plan` の標準入力に渡す。
既存の受け入れ（AC-8）が同じ道具立てで「apply のあとに plan すると差分なし」を
確かめているので、その隣に置く。

**(3) が EX-3 の実行可能な仕様になる。** 「`export` は課題の有無を見ないが、
書き込みの限定は破らない」を、2つの終了コードとして書き表せる。

**UC-1 の往復**は「雛形として使える」ことの直接の証明である。
`export` → `key` と `name` を書き換え → 未作成のキーに `apply` → その新プロジェクトを
`export` → 最初の出力と `key` / `name` 以外が一致する。
[§4.1](core-reconciler.md#41-フェーズと-read) の既定課題種別の枠の引き継ぎを通るので、
新規プロジェクトの経路も同時に踏む。

**AC-8（apply 後の plan は差分なし）と EX-18 (1)(2) は同じ性質の受け入れ基準である。**
どちらも「ツールが作った状態を、ツール自身が『もう何もすることがない』と読む」ことを言っている。

## 7. `export` が何でないか

### EX-19: ドリフト検出の道具ではない

| 決定 | 内容 |
| --- | --- |
| EX-19 | `export` はいまの姿を雛形の出発点として書き出すだけであり、ツールは2つのマニフェストを比較しない。README にそう明記する |

`export` があれば「CI で書き出してリポジトリの Yaml と diff する」というループを
利用者が自分で組める。それを禁じる手段は無いし、禁じたいわけでもない。

しかし**ツールが約束するのは「いまの姿を書く」ところまで**である。
差分を監視すること、ずれを報告すること、ずれを直すことはいずれも約束しない。
[AGENTS.md](../../../AGENTS.md) の「一度きりの初期化」と README の
"It keeps no state ... no drift detection" は `export` を足しても真のままであり、
真のままであることを文章で守る。

### EX-20: Web UI に載せ、別のページに置く

| 決定 | 内容 |
| --- | --- |
| EX-20 | `export` を Web UI にも載せる。Apply とは別のページに置き、書き出した Yaml を Apply のエディタへ送る導線は持たない。画面の形は [CLI と Web UI §2.7](cli-and-web-ui.md#27-export-ページ)（WU-27〜WU-32） |

NFR-6 が禁じているのは**ロジックの二重実装**であって、UI 面の機能差ではない。
`toManifest` と `serializeManifest` が core にある（EX-1）ので、Web は `createExport` を呼ぶだけで済む。

当初この決定を保留したのは、写像の正しさではなく画面の形が決まっていなかったためである。
残っていた論点は1つだった。

- 読み込んだ結果でエディタを上書きすることと [WU-3](cli-and-web-ui.md#23-wu-3-入力が変わったら計画を破棄する)（入力が変われば計画を破棄する）の関係

**別のページに置き、エディタへ送らないことで、この関係そのものが生まれない**（WU-31）。
1回の来訪で書き出しと適用を両方やることはまれで、書き出したものを使い回すには
`key` と `name` を書き換える必要がある（EX-3）ので、送る導線が省く手間は小さい。

`export` がもっとも効くのは P3（Yaml を書かない担当者）であり、その層は CLI を持たない。
これが載せる理由である。

## 8. 判断理由のまとめ

| ID | 決定 | 採らなかった案と理由 |
| --- | --- | --- |
| EX-1 | `read` → `toManifest` → `serialize` の3段。core に置く | `Reconciler.export()` を足す。リソースを1つ増やす作業が増え、NFR-8 の約束が薄まる。`apps/cli` に写像を置く案は Web で二重実装になる |
| EX-2 | 権限を問わない | スペース管理者を要求する。R-5 を撤回した後に `export` だけ残すと、プロジェクト管理者が自分のプロジェクトを雛形にできない |
| EX-3 | 課題の有無を見ない | V-B3 相当のゲートを置く。稼働中のプロジェクトを雛形にする用途が消え、雛形にできるプロジェクトが実質なくなる |
| EX-4 | `hookUrl` は取得値をそのまま書く | プレースホルダに置き換える。利用者が環境ごとに変える場所を選べず、出力だけでは同じ設定を再現できない |
| EX-6 | `oldname` を書き出さない | 推測して復元する。`oldname` は移行元のヒントであり、あるべき姿を表すスナップショットには対応するものが無い |
| EX-8 | チーム経由の個人参加者を `members` に残す | 落として V-A16 を避ける。読み戻した計画がその人の個人参加を削除する |
| EX-9 | 表現できない実状は失敗 | 書き出して `validate` に落とさせる（自己矛盾）／警告して書き出す（使えないファイルがコミットされる）／改名して辻褄を合わせる（あるべき姿の捏造） |
