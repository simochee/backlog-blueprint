# マニフェストのバージョニング方針

最終更新: 2026-09-19

依頼者から「IaC のマニフェストのバージョニングがどういうものか分からない」という話があったため、
一般的なやり方の整理と、本プロジェクトでの決定をまとめる。

## 1. そもそも何を解決したいのか

「マニフェストのバージョニング」は、実は別々の2つの問題が同じ言葉で呼ばれている。

### 問題A: 互換性 — 古いファイルと新しいツールが噛み合わない

一度配った Yaml は、書いた人のリポジトリに何年も残る。
その間にツール側でキー名を変えたり構造を変えたりすると、次のどちらかが起きる。

1. 古いファイルが読めなくなる（利用者全員が一斉に書き換える羽目になる）
2. 読めるが**意図と違う解釈をされる**（キーが黙って無視され、設定が効いていないことに気付かない）

2 のほうが圧倒的に危険。バージョニングの本質はここを防ぐこと。

### 問題B: 開発体験 — 書くときに補完と検証が欲しい

何が書けるか分からない Yaml を手で書くのは苦痛。
エディタで補完が出て、間違いに赤波線が出てほしい。

**この2つは解き方が違う。** 混同すると「バージョンを付けたのに補完が効かない」
「補完は効くが互換性は何も守られていない」という中途半端な状態になる。

## 2. 実在するツールがどうしているか

| ツール | やり方 | 評価 |
| --- | --- | --- |
| Kubernetes | `apiVersion: apps/v1` + `kind: Deployment`。`v1alpha1` → `v1beta1` → `v1` と段階を踏み、サーバ側で新旧を相互変換する | 最も厳密。ただし変換機構を持つコストが非常に高い |
| Terraform | マニフェスト自体にバージョンは無い。`required_version = "~> 1.5"` で**ツール側のバージョン**を宣言させる | 「ファイルの世代」ではなく「必要なツール」を表明する発想 |
| GitHub Actions | バージョンフィールドが**存在しない**。壊れる変更をしないと決めている | 一番シンプル。その代わり永久に互換性を背負う |
| Dependabot | `version: 2` という整数1つ。数年に一度しか上がらない | 「大改造したときだけ上げる」割り切り |
| Biome | `"$schema": "https://biomejs.dev/schemas/1.9.4/schema.json"` と **URL にバージョンを埋め込む** | 補完が効き、かつファイルに世代が刻まれる |
| Docker Compose | かつて `version: "3.8"` が必須だった。**現在は非推奨**で、書くと警告が出る | バージョンフィールドを付けたが運用しきれず捨てた実例 |

Docker Compose の例が示唆的で、**バージョンフィールドは付けるのは簡単だが、
使いこなす（複数バージョンを並行サポートし、変換し、廃止する）のは重い**。
多くのツールは付けたフィールドを一度も上げないまま終わる。

## 3. 本プロジェクトの決定

### 採用: `$schema` にバージョン入りの URL を書く（Biome 方式）

```yaml
# yaml-language-server: $schema=https://<host>/schema/0.1.0/project.json
key: PROJ_A
name: プロジェクトA
```

| 決定 | 内容 |
| --- | --- |
| D-1 | JSON Schema をバージョン付き URL で配布する。URL のパスにバージョンを含める |
| D-2 | **スキーマのバージョン = CLI の semver** とし、別体系を作らない |
| D-3 | 過去バージョンの URL は消さない。古いリポジトリでエディタ支援が壊れないため |
| D-4 | `apiVersion` / `kind` キーは**今は導入しない** |
| D-5 | 未知のキーはエラーにする（strict parse） |

### なぜ `apiVersion` を今は入れないか

入れないことによる将来のリスクが小さいから。

- `apiVersion` を**後から任意キーとして足すのは非破壊変更**。
  省略時は v1 とみなせばよく、既存ファイルは1文字も変えずに動き続ける
- つまり「将来必要になったら足せる」ので、今は使わないフィールドを利用者に書かせる必要がない
- Kubernetes 式の複数バージョン並行サポートは、1リポジトリの設定管理ツールには過剰

### D-5 が実質的なバージョン安全装置である理由

問題Aで挙げた「2. 読めるが意図と違う解釈をされる」を防ぐのは、
`apiVersion` ではなく **strict parse** のほうである。

```yaml
# 新しい CLI で追加されたキーを、古い CLI に食わせた場合
issueTypes:
  - name: バグ
    color: "#990000"
    templateSummary: "再現手順:"   # 古い CLI が知らないキー
```

- 未知キーを無視する実装 → テンプレートが設定されないまま「成功」と報告される（最悪）
- 未知キーをエラーにする実装 → 「このキーは知りません。CLI を更新してください」で止まる（正しい）

`$schema` の URL は YAML コメントなのでツール側から互換性判定に使うのは筋が悪い。
だから互換性は strict parse が担い、`$schema` は**エディタ支援に専念させる**。
これが問題Aと問題Bを分けて解くということ。

### 破壊的変更をするときの手順

1. CLI の major を上げる
2. 新しいバージョンの JSON Schema を新しい URL で公開する（旧 URL は残す）
3. 旧形式のキーを検出したら、**エラーメッセージで新形式への書き換え方を示す**
   （黙って解釈しない。移行方法を人間に伝えるところまでがツールの責任）

自動変換コマンド（`blueprint migrate` のようなもの）は、
実際に破壊的変更が必要になった時点で検討する。今から用意するものではない。
