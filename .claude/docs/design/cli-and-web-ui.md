# CLI と Web UI の設計

最終更新: 2026-09-23
前提: [要件定義 FR-6 / FR-7](../requirements/requirements-definition.md#fr-6-cli) / [plan の出力仕様](plan-output.md) / [検証パイプライン](validation-pipeline.md)

CLI と Web UI は「入出力の違い」だけを担う（要件定義 §7）。
検証も計画も適用も core が持つので、ここで決めるのは**受け取り方と見せ方**だけ。

## 1. CLI

### 1.1 コマンド体系

```
backlog-blueprint <command> [options]

Commands:
  validate       Validate a manifest without contacting Backlog
  plan           Show what apply would do (read-only)
  apply          Apply the manifest to Backlog
  export <key>   Write an existing project out as a manifest (read-only)
```

| コマンド | ネットワーク | API キー | 走る検証 |
| --- | --- | --- | --- |
| `validate` | 使わない | 不要 | S1〜S4（[検証パイプライン](validation-pipeline.md)） |
| `plan` | GET のみ | 必要 | S1〜S7 |
| `apply` | GET + 更新系 | 必要 | S1〜S7 → 確認 → 実行 |
| `export` | GET のみ | 必要 | S5（[EX-2](export.md#ex-2-実行者はスペース管理者であることを要求する)）と、**自分が組み上げたマニフェストに当てる S3 / S4**（[検証パイプライン §4](validation-pipeline.md#export-は自分の出力に-s3--s4-を当てる)）。マニフェストを入力に取らないので S1・S2 は走らず、S6 は `read()` だけ、S7 は走らない |

### CL-1: `validate` を追加する

要件定義 FR-6.2 は `plan` / `apply` の2つを規定していたが、`validate` を足す。

| 決定 | 内容 |
| --- | --- |
| CL-1 | `validate` は Backlog に一切アクセスせず、マニフェスト単体で判定できる検証だけを走らせる |

`plan` でも同じ検証は走るので機能的には重複する。それでも分ける理由。

1. **API キーを持たない CI で回せる。** PR のチェックに秒で回せる静的ゲートができる
2. **展開に使う値が揃わない環境で回せる。** そのため `validate` では V-A4（`${ENV}` の解決）を警告に下げる
3. **書いている最中の確認に使える。** ネットワークもレート制限も消費しない

`plan` との責務の違いは「Backlog を見るかどうか」の一点で説明できる。
これは覚えやすく、`--dry-run` のようなフラグの重ね掛けより分かりやすい。

**採らなかった案: `plan --offline`。**
「オフラインの plan」は語義矛盾で、plan の約束（apply で何が起きるか）を果たせない。
フラグで別物にするより、別のコマンドにするほうが正直。

### 1.2 オプション

接続に関するもの。全コマンドが持つ。

| オプション | 環境変数 | 既定 | 内容 |
| --- | --- | --- | --- |
| `--space <domain>` | `BACKLOG_SPACE` | — | `example.backlog.com` / `example.backlog.jp` |
| `--no-color` | `NO_COLOR` | — | 色を付けない |
| `-h, --help` / `-V, --version` | — | — | |

マニフェストを入力に取るもの（`validate` / `plan` / `apply`）。

| オプション | 既定 | 内容 |
| --- | --- | --- |
| `-f, --file <path>` | **必須** | マニフェストのパス。`-` で標準入力 |
| `--output <format>` | `text` | `text` / `json` |

コマンド固有。

| コマンド | 引数・オプション | 内容 |
| --- | --- | --- |
| `plan` | `--show-unchanged` | `noop` の Action も表示する |
| `apply` | `-y, --auto-approve` | 確認プロンプトを省略する |
| `export` | `<key>` | 書き出すプロジェクトのキー。**必須・1つ**（CL-7） |

API キーは `BACKLOG_API_KEY` からのみ受け取る。

### CL-2: `--api-key` オプションを提供しない

| 決定 | 内容 |
| --- | --- |
| CL-2 | API キーを渡す手段は環境変数だけ。コマンドライン引数では受け取らない |

引数に書くと `ps` で他ユーザーから見え、シェル履歴に残り、CI のコマンドログに出る。
NFR-3（API キーをログ・出力・エラーに出さない）を守っても、
渡し方が漏洩経路になっていては意味がない。

`--space` を引数でも受けるのは、これが秘匿値ではなく、
複数スペースを切り替える実運用が想定できるため。

### CL-3: `-f` は1回だけ。複数ファイルを受け取らない

1ファイル = 1プロジェクト（要件定義 §2.1）を、CLI の呼び出し単位にもそろえる。

複数を受け取ると、「2つ目のプロジェクトの途中で失敗したとき、1つ目は適用済み」という
プロジェクト境界をまたいだ部分適用が生まれる。中断レポート（FR-4.4）が
「どのプロジェクトのどこまで」を表現する必要が出て、構造が一段複雑になる。
シェルのループで回せば済む話に、その複雑さを払う理由がない。

`export` は位置引数で同じ不変条件を守る（CL-7）。

### CL-7: `export` は位置引数1つ。`-f` も `--output` も持たない

| 決定 | 内容 |
| --- | --- |
| CL-7 | `export <key>` はプロジェクトキーを**位置引数**で1つだけ受け取る。`-f` / `--output` / `--show-unchanged` / `-y` は定義しない。持つのは `--space` と `--no-color` だけ |

**キーの形（`^[A-Z0-9_]+$`）を判定するのは CLI ではなく core の `createExport` である**
（[EX-3](export.md#ex-3-プロジェクトの存在は要求するが課題の有無は見ない)）。CLI が担うのは
commander が見る引数の形——位置引数が1つか、未知のオプションが無いか——までで、
プロジェクトキーという値そのものの規則は S3 の `key` と同じものであり、置き場所も同じでよい。

**CL-3 の不変条件は「1回の実行で扱うプロジェクトは1つ」であって、「`-f` というフラグ」ではない。**
`-f` がオプションなのは、マニフェストが**ファイルパス**であり `-` で標準入力も表すからで、
値の性質がオプション向きだからである。`export` の対象は動作を変える修飾子ではなく**主語**なので、
位置引数にする。`export A B` は commander が拒むので、CL-3 と同じ約束を同じ強さで守る。

`--output json` を持たない理由は、**`export` の出力がマニフェストそのもの**だからである。
マニフェストの形式は Yaml と決まっており（要件定義 §2.1）、`plan` の JSON のような
「同じ内容の別の見せ方」にはあたらない。

`-o <path>` のような出力先のオプションも持たない。シェルのリダイレクトと同じことを
2通りで書けるようにするだけで、既存ファイルを上書きしてよいかの判断（`--force` が要るか）が
新たに生まれる。

**採らなかった案: `export -f <既存の yaml>` で実状を書き戻す。** コメントや並びを保てる可能性はあるが、
「書き出し」ではなく「差分の取り込み」の導線になり、非スコープの境界が曖昧になる。

### CL-8: `export` の標準出力は Yaml だけ

| 決定 | 内容 |
| --- | --- |
| CL-8 | stdout には Yaml しか書かない。stderr には課題件数の案内（1件以上のときだけ）を出す。警告は無い |

`--no-color` は stderr にだけ効く。stdout は Yaml なので色を付ける経路がそもそも無い。

警告が無いのは、`export` が S6 / S7 を走らせないためである
（V-A15 も V-A16 も判定に計画が要る）。発生源が無いところに節を用意しない。

```
$ backlog-blueprint export PROJ_A > projects/PROJ_A.yaml
NOTE  PROJ_A holds 43 issues, so plan and apply will refuse it as a target (V-B3)
  → to use this manifest as a template, change key and name before you apply it

```

行頭は既存の `ERROR` / `!` と同じく語のあとに2スペース。
1件のときは単数形にする（`holds 1 issue`）。

`→` の行の末尾にピリオドを置かないのは既存の `hint` に揃えるためである。

### CL-9: `export` の終了コードは 0 と 1 だけ

| 決定 | 内容 |
| --- | --- |
| CL-9 | 0 が「書き出した」、1 が「エラー」。2 は使わない。診断の集計行は `N export errors. Nothing has been written.` |

`plan` の 2（差分あり）に対応するものが `export` に無い。書き出すか、書き出さないかの2つしかない。

集計行が `Nothing has been applied.` ではないのは、`export` が適用しないためである。
要件定義 §5.3 が `validate` と `plan` でその行を添えないと決めたのと同じ理由で、
**言う相手のいない文を出さない。** `export` は「書き出さなかった」ことを言う必要があるので、
そこだけ差し替える（EX-17 が stdout を空に保つので、この行は事実を述べている）。

### 1.3 標準出力と標準エラー出力

| ストリーム | `--output text` | `--output json` |
| --- | --- | --- |
| stdout | 計画・結果の本文 | **JSON だけ** |
| stderr | 進捗、確認プロンプト、警告、エラー | 進捗、確認プロンプト、警告、エラー |

**警告の出し先はモードで変わる。** `--output text` では計画本文の `Warnings:` セクションに出し、
stderr には写さない（二重に出さないため）。`--output json` では JSON に `diagnostics` として入り、
人が気づけるよう stderr にも整形して出す。

`--output json` のとき stdout を JSON 専用にするのは、
`blueprint plan -f x --output json \| jq` が素通しで動くため（PO-7）。
検証エラーも警告も stderr に出るので、JSON が汚れることはない。

### 1.4 確認プロンプト

```
Do you want to apply these changes?
  Only "yes" will be accepted to confirm.

  Enter a value:
```

| ID | 決定 | 理由 |
| --- | --- | --- |
| CL-4 | `apply` は既定で確認を求める。`--auto-approve` / `-y` で省略 | 課題種別・ステータスの削除を含むため、手元での誤爆に対する砦を1枚残す |
| CL-5 | `yes` の**全文入力**を求める。`y` では通さない | 1文字だと Enter 連打で通ってしまう |
| CL-6 | 標準入力が TTY でないときは、`--auto-approve` が無ければ**エラーで停止**する | CI で確認待ちのままハングするのが最悪。明示的に落として、フラグを足させる |

CL-6 のエラーメッセージ。

```
ERROR  apply requires confirmation, but stdin is not a terminal.
  → pass --auto-approve to skip the confirmation
```

**採らなかった案: 削除を含むときだけ確認する。**
安全側と手間のバランスは良いが、「いつ止まるか」が実行してみるまで分からない挙動になる。
CI で `--auto-approve` を付け忘れたとき、マニフェストの内容次第で通ったり落ちたりする。
再現性が売りのツールが、自分の挙動を非決定的にするのは筋が悪い。

### 1.5 終了コード

| コード | `validate` | `plan` | `apply` | `export` |
| --- | --- | --- | --- | --- |
| 0 | 検証を通過 | 差分なし | 成功 | 書き出した |
| 1 | 検証違反、その他のエラー | エラー | エラー（中断を含む） | エラー |
| 2 | （未使用） | 差分あり | （未使用） | （未使用） |

確認プロンプトで拒否した場合（`--output json` の `result` が `rejected`）は **1** を返す。
表に無いが、0 を返すと「成功」と区別できなくなる。適用していないことは `result` が示す。

`apply` の中断（FR-4.4 の部分適用）に専用のコードを与える案は採らない。
要件定義 FR-6.3 の表が `apply` のエラーを 1 に定めているため。

> 「何も適用されずに検証で止まった」と「途中まで適用されて止まった」は
> CI の後処理としては扱いが違う（後者は人間の確認が要る）。
> 専用コード（例: 3）を割り当てる価値はあるが、終了コードの定義は要件定義側の決定事項なので、
> ここでは変えない。必要になったら要件定義 FR-6.3 を更新する。
> 当面は `--output json` の `result` が `aborted` かどうかで判別できる。

## 2. Web UI

### 2.1 画面構成

**Apply と Export の2ページ。Apply は4ステップのステッパー。** ページはハッシュで表し、ルーティングのライブラリは持たない（WU-1 / §2.7）。

| ID | 決定 | 理由 |
| --- | --- | --- |
| WU-1 | URL が表すのは**どのページか**（`#/` と `#/export`）だけ。ステップや入力は URL に載せない。ハッシュで持ち、ルーティングのライブラリは入れない | 状態はメモリ上にしか無い（FR-7.4）ので、リロードすると全て消える。ステップを URL に載せると、開き直したときにその状態を復元できず URL が嘘になる。**ページは状態ではなく来訪の目的**なので、載せても嘘にならず、ブックマークと戻るボタンが効く。ハッシュにするのは、GitHub Pages に SPA フォールバックの設定が要らないため。行き先が2つしか無いので、ライブラリを入れても `hashchange` を購読する以上の仕事が無い |
| WU-2 | Vite の `base` を `/backlog-blueprint/` にする | GitHub Pages のサブパス配信（要件定義 §7.1） |
| WU-4 | UI は React で組む | WU-3（入力が変わったら計画を破棄する）を、書き忘れない行儀ではなく**入力の派生状態**として構造で守れる。素の DOM 操作だと、入力のハンドラごとに破棄を書く必要があり、1つ漏れると「見た計画と違うものが適用される」が起きる |
| WU-15 | 結果が1つだけ返る操作（connect / plan）は React の **Action** として書く（`useActionState`）。`connecting` / `planning` のような保留中の真偽値を自前で持たない。**apply は Action にしない** | 自前で持つと、`try` / `finally` の全ての経路で倒し忘れないことが正しさの条件になる。押しっぱなしの Connect が残るのは、通信が落ちたときという最も確かめにくい経路である。React に持たせれば、保留中は Action が解決するまでで定義され、経路が1つ増えても書き足す場所が無い。**Action は `startTransition` の中から呼ぶ。** `<form action>` に渡す案は採らない — React 19 は Action の後にフォームを reset するので、非制御の API キー欄が空になる。§2.4 によりその欄は制御できず、`defaultValue` も置けない（秘匿値が DOM の属性に出る）。空になったのか打っていないのかが画面から区別できなくなる。**apply を除くのは、Action の中で置いた state がその Action の解決まで画面に出ないため。**終わるまで中途半端な姿を見せないための仕組みだが、apply は進捗を1件ずつ出すのが仕事なので、包むと進捗が全部終わってからまとめて出る。`useOptimistic` で流す案も、await の後に呼ぶ時点でAction の外からの更新になり、出したそばから消える。apply が保留中の真偽値を持たないことはWU-17 で別に満たす |
| WU-16 | 入力が落ち着くのを固定の待ち時間で測らない。検証は `useDeferredValue` で**後回しの描画**として走らせる | 300ms の待ちは、速く打つ人には長すぎ、重いマニフェストには短すぎる数字を1つ選ぶことでしかない。後回しの描画なら、React が打鍵を優先したうえで手が空いた時点で走らせ、まだ始めていない分は次の打鍵が来た時点で捨てる。**これは待ち時間を短くする決定ではなく、待つのをやめる決定である。** 走る条件は「入力が止まった」ではなく「手が空いた」なので、ゆっくり打つ人には打鍵ごとに走り、書きかけの行に対する診断も出る。沈黙を待つあいだ診断が出ないことと引き換えに取る。待ち時間の state と `setTimeout` が消え、検証結果は「落ち着いた入力の派生」そのものになるので、WU-3 の印（`fresh`）がそのまま古い結果を弾く |
| WU-17 | apply が実行中かどうかを別の真偽値で持たず、**適用の記録から導く** | `execute` は必ず `finished` か `aborted` で終わる（[core](core-reconciler.md) §7）ので、終わったことは記録そのものが持っている。真偽値を別に置くと `結末あり + 実行中` という起きえない状態が書ける形になり、実際に毎回書かれていた（最後のイベントを畳んだ記録がそれである）。導けばその状態は表せない |
| WU-18 | 描画中に投げられた例外は**段ごとに**受け止め、落ちた段の中身だけを差し替える。**受け止めた内容は画面に出さない** | 1枚で画面全体を覆うと、apply の最中に落ちたときに進捗と中断レポートごと消え、離脱の警告（§2.4）も同時に外れる。適用済みのものが残っているのに、何が残っているかを言える画面が無くなるのが最悪である。段ごとなら、落ちた段だけが差し替わり、他の段と走っている適用は残る。**内容を出さないのは、描画中の例外が利用者の直せるものではないため。** マニフェストの誤りは検証が行番号付きで出す（§2.2）ので、ここまで来るのは画面の不具合である。画面に出せるのは「この段は表示できない」ことと、やり直す手段だけで、中身は console に残る React の既定の報告に任せる。**境界が要るのはエディタの遅延読み込み（WU-12）だけが理由ではない。** WU-15 の Action は、値を返さずに throw すると拒否された thenable が state に入り、次の描画でそれが投げ直される。受け止める場所が無いと root ごと落ちる |
| WU-19 | **React Compiler** を有効にし、畳めない部品があれば**ビルドを落とす**（`panicThreshold`） | どこに `useMemo` を置くかを部品ごとに判断しなくて済む。落とす側に倒すのは、既定が「畳めない部品は素通し」だからである。素通しになっても画面は動くので、遅くなったことに誰も気付かない。実際、入れた時点で `App` は`for await`（適用の進捗を購読する loop）ひとつのために丸ごと対象外になっていた。loop は画面の外へ出した。**このリポジトリでは、畳ませる前に依存を見える形にする必要がある。** API キーと環境変数の入力値はモジュールに置く（§2.4）ので、描画中にそれを読む式の依存は Compiler から見えない。見えないまま畳むと、API キーを打っても Connect が押せるようにならず、環境変数を打っても検証が走らない — どちらも実際にそうなった。直し方は2つで、**購読の返り値に載せる**（`hasApiKey` は snapshot の一項目にした）か、**印を引数に取る**（検証は `validatedFor(印になる入力)` で、同じ印なら同じ結果だと関数の外から言える形にした）。`useMemo` の依存配列に書くのは効かない — Compiler は書かれた配列を採らず、式が触っているものから依存を引き直す。どちらにも直せない入力欄の初期値だけは `"use no memo"` で畳ませない |
| WU-13 | 環境変数の入力欄はボタンの中に畳み、未入力の件数をバッジで出す | `${NAME}` を書いていないマニフェストでも欄の枠が常に画面を占めていた。畳むとマニフェストが横幅を全部使える。ここはモーダルでよい。confirm.tsx が背面を生かしているのは WU-3 を到達可能に保つためで、環境変数を打つあいだマニフェストを触れなくても失われるものは無い |
| WU-14 | 配色は **Catppuccin**（明 Latte / 暗 Mocha）。ページは Radix のトークンを差し替え、エディタは公式の `@catppuccin/codemirror` を使う | ページとエディタが別の配色だと、画面の中にもう1つ別のアプリが埋まっているように見える。Catppuccin の中立色はちょうど 12 段（crust / mantle / base / surface0-2 / overlay0-2 / subtext0-1 / text）あり、Radix のグレー 12 段と役割の並びが一致するので、中間値を作らずに写せる。面の重なりは crust（地）→ mantle（カード）→ base（エディタ）の順に明るくする |

| WU-7 | 接続できたら、利用者名と並べて**スペース名**（`GET /api/v2/space` の `name`）を出す | ドメインは打った本人にしか読めない識別子で、打ち間違えても形は正しいままになる。スペース名を返すと「意図した先に繋がったか」を人が確かめられる。core-reconciler §297 が `GET /api/v2/space` を採らなかったのは既定名の言語判定の話で、ここは目的が違う |

### 2.2 各ステップ

#### Step 1 Connect

- スペースドメインと API キーを受け取り、`GET /users/myself`・`GET /space`・`GET /rateLimit` を叩く
- **V-B1（キーが有効）と V-B2（スペース管理者）をここで判定する。** 管理者でなければ先へ進ませない
- 接続中のユーザー名・スペース名（WU-7）と、更新系レート制限の残量を表示する（FR-7.6）
- ドメインを打った時点で API キーのページへの導線を出す（WU-8）
- 入力欄は `type="password"` / `autocomplete="off"`

権限の確認を最初に置くのは、マニフェストを書き終えてから「権限がありません」と言われる
順序を避けるため。CLI では S5 が S1〜S4 の後に来るが、Web では逆順になる。
これは矛盾ではなく、**入力を得られる順序が違う**だけ（CLI は起動時に全部揃っている）。

#### Step 2 Manifest

- Yaml の貼り付け欄。ファイルのドラッグ&ドロップも受けるが、読み込んだ内容は同じ欄に入る
- 打鍵の合間に手が空くたびに **S1〜S4（`validate` と同じ検証）をブラウザ内で走らせる**（WU-16）。
  行番号付きでエラーを出す
- `${NAME}` が見つかったら、その名前ごとに入力欄を動的に生成する（FR-7.5）。
  値は通常のマニフェスト値として扱い、計画に表示する（E-8）

環境変数の入力欄を「マニフェストから生成する」のが要点。
先に空欄を並べて名前を書かせると、綴り間違いが検証を素通りする。

#### Step 3 Plan

- `read` を実行し、S5〜S7 を判定して計画を描画する
- CLI と同じ `Action[]` を同じ分類で表示する。記号の代わりにバッジを使う
- 警告セクション、更新系の件数と推定秒数、`--output json` 相当をコピーするボタン
- 「Apply」は確認ダイアログを挟む（CLI の確認プロンプトに対応）

送信層のクライアントを state に載せないのは、不変条件を単純に保つためである。
「API キーを持つものはモジュールスコープにしかない」と言い切れれば、grep で確かめられる。
「表示も永続化もしないから state でもよい」と例外を作ると、次に似たものが出たときに
同じ判断を繰り返すことになる。接続が有効かどうかは、値ではなく印だけを state に置けば表せる。

**Step 3 の推定秒数は CLI と同じ形式で出す**（[plan の出力仕様 §1.3](plan-output.md#13-フッタ)）。
60 秒以上は `2m 30s`。描画の関数は core が持ち、Web が書き写さない（NFR-6）。

**表示するユーザー名は `GET /users/myself` の `userId`**（ログイン ID）。`access` に書くのと同じ値なので、
画面に出ている名前をそのままマニフェストに写せる。

**作成されたプロジェクトへのリンクは `https://<space>/projects/<KEY>`**（実測）。

#### Step 4 Apply

- Executor の `AsyncIterable`（C-4）をそのまま購読して進捗を描く
- 完了 → サマリと、作成されたプロジェクトへのリンク
- 中断 → 適用済み / 失敗 / 未適用 の3リストとエラー本文、レポートのコピーボタン、
  「同じマニフェストでもう一度実行すれば続きから進む」の案内

### WU-5: 確認は `yes` の全文入力を求めない

| ID | 決定 |
| --- | --- |
| WU-5 | Web の確認はダイアログの Cancel / Apply。CL-5 の「`yes` と全文で打たせる」は持ち込まない |

CL-5 の理由は「1文字だと Enter 連打で通ってしまう」ことだった。**これはターミナル固有の事故**で、
意図せず押しっぱなしになる入力手段がダイアログには無い。文面は `APPLY_CONFIRMATION` の1行目を使う。

### WU-6: 一致している行を展開する手段を持つ

| ID | 決定 |
| --- | --- |
| WU-6 | Step 3 に「一致している行も表示する」の切り替えを置く。CLI の `--show-unchanged`（PO-9）に当たる |

置かないと Web だけ情報が減る。`noop` を既定で隠す理由（PO-9）は Web でも変わらないので、既定は隠す。

### 2.3 WU-3: 入力が変わったら計画を破棄する

| 決定 | 内容 |
| --- | --- |
| WU-3 | 次のいずれかで算出済みの計画を破棄し、Step 3 をやり直させる。**(a)** マニフェスト・環境変数の値・接続情報が変わったとき。**(b)** その計画で apply が完了または中断したとき |

CLI では `apply` が毎回 read から計算し直すので（FR-4.1）この問題が起きない。
Web ではステップが分かれている以上、**見た計画と適用される内容がずれる窓**が構造的に生まれる。
plan と apply の間に1文字でも変えられたら、その計画は無効として扱う。

**(b) を入れるのは、CLI に FR-4.1（apply は毎回 read から計画を算出し直す）があるため。**
Web はステップが分かれているので、同じ計画に2回目の Apply を押せてしまうと
1回目の適用でスペースの状態が変わった後の計画を持たないまま実行することになる。
`+ project` は 400 で即中断し、`+ status` は重複作成になる。
**「適用の記録を残すこと」と「同じ計画をもう一度適用できること」は別で、残すのは前者だけ。**

**確認ダイアログは Apply を押したときだけ開く。** 入力が変われば閉じ、
**計画をやり直した後に自動で再表示しない**。「Apply を押した結果としての確認」なので、
開いているかどうかも計画と同じく入力の派生状態として持つ。

これは「plan で見たものが apply される」という本ツールの中心的な約束を、
UI の側で守るための決定。

### 2.4 API キーの扱い

| 規則 | 内容 |
| --- | --- |
| 保持場所 | API キーはモジュールスコープの変数のみ。`localStorage` / `sessionStorage` / IndexedDB / URL に書かない（FR-7.4）。**API キーを内包する送信層のクライアントも同じ**。React の state に載せない |
| 入力欄 | `type="password"`、`autocomplete="off"` |
| 表示 | API キーを計画・進捗・エラーに含めない（NFR-3） |
| 離脱時 | apply の実行中のみ `beforeunload` で警告する。適用途中でタブを閉じると中途半端な状態が残るため |

### 2.5 レート制限とブラウザ

ブラウザは `access-control-expose-headers` が返らないため `X-RateLimit-*` を読めない（実測）。
core は Node でもブラウザでも常に `GET /rateLimit` の本文を使う（X-3）ので、
Web UI 側で特別な分岐は要らない。

### 2.6 スペースのユーザーとチームの一覧

`access` に書くのはログイン ID とチーム ID（A-6）で、どちらも Backlog の画面では探しにくい
（ユーザー一覧が大きく出すのは表示名で、ログイン ID ではない。チーム ID は画面に出ない）。打ち間違えれば V-B4 / V-B5 が
`plan` で止めるが、止まるのはマニフェストを書き終えた後である。書く最中に写せる元を画面に置く。

| ID | 決定 | 理由 |
| --- | --- | --- |
| WU-20 | ヘッダーに **Users** と **Teams** の2つのボタンを置き、押すと画面の右に**サイドペイン**が開く。初期表示では閉じている。**ペインは同時に1枚しか開かない。** 開いているペインのボタンをもう一度押すか、ペインの Close で閉じる。ユーザーとチームは別のアイコンで区別する | ステップの流れの外にある道具なので、ステッパーの段にしない。**モーダルにしない**のは、一覧から写してマニフェストに貼るのが使い方で、背面のエディタに触れないと用をなさないため（WU-13 の環境変数と逆の判断）。2枚並べると本文の幅（WU-10）を2枚分削るうえ、どちらのペインから写したかが画面から読みにくくなる |
| WU-21 | ボタンは**接続できるまで押せない**。接続の印（WU-3）が変わって接続が無効になれば、開いているペインは閉じ、ボタンもまた押せなくなる | 接続できたことは V-B2 を通ったこと、つまりスペース管理者であることを意味する（§2.2 Step 1）。スペース管理者でない人がこの一覧を使っても、その人は plan から先へ進めないので、写した値の行き先が無い。送信層も接続のときに開く（`openTransport`）ので、接続前には取りに行く手段がそもそも無い |
| WU-22 | 一覧は**初めて開いたとき**に取得する（ユーザーは `GET /api/v2/users`、チームは `GET /api/v2/teams`）。**閉じても一覧・絞り込みの文字列・選択は保持する。** 取り直すのは Reload を押したときだけ。保持したものは接続の印に紐づけ、印が変われば捨てる | 開くたびに取ると、閉じて開き直すたびに選択が消え、読み取りの枠も減る。接続前に先回りして取らないのは、開かない人の分まで読み取りを使うため。**印に紐づけるのは、別のスペースに繋ぎ直した後に前のスペースの一覧が残ると、存在しない人を写させるため。** 同じスペースへの繋ぎ直しでも捨てるのは、API キーの書き換え（別の人として繋いだ可能性）と見分けないためで、WU-3 と同じ線引きである |
| WU-23 | コピーは**選択した要素**を、`access.teams` / `access.members` / `access.administrators` の直下にそのまま貼れる**段付きの Yaml の系列**（`    - yamada # 山田 太郎`）で書き出す。ユーザーは**ログイン ID**（`userId`）を、チームは**チーム ID**（A-6）を写し、行末に表示名・チーム名をコメントで付ける（EX-8 と同じ規則）。**メールアドレスはコメントに入れない** — マニフェストは雛形として配られリポジトリに残るので、個人情報を広める経路になる。人を見分けるのに要るのは画面で見慣れた表示名で、重複しないことはログイン ID が既に担っている。書き出しは core が持ち、`export` と同じシリアライズ設定と EX-5 のエスケープを通す | 段付けを含めるのは、エディタに複数行を貼ると2行目以降が行頭から始まり、段を揃え直す手間が行数分かかるため。段の深さは `access` がトップレベルにあるので一意に決まる。引用の要否を Web で判断しない — `true` / `123` のような名前は引用しないと文字列として読めず、`${` を含む名前は EX-5 を通さないと環境変数として展開される。**書く側の規則を2か所に持つと、片方だけ S1 とずれる**（serialize.ts の Why-not）。表示名ではなくログイン ID を写すのは、V-B4 が照合するのがログイン ID だから（§2.2 の「表示するユーザー名」と同じ理由） |
| WU-24 | 各要素の行に**その1件だけをコピーするアイコンボタン**を置く。チェックボックスによる複数選択とコピーはそのまま残す | 1人足すだけのために、選ぶ → Copy → 選択を外す、の3手を踏ませない。選択を外し忘れると、次にまとめてコピーしたときに前の1人が紛れ込む。1件のコピーは選択を触らないので、両方を並べても互いの状態を壊さない |
| WU-25 | 画面上部のヘッダー（タイトルと Users / Teams のボタン）は**スクロールしても上端に留める**（`position: sticky`） | 一覧が要るのはマニフェストを書いている最中で、その時点で画面は Plan や Apply まで伸びている。ボタンが先頭にしか無いと、開くたびに上まで戻り、戻ってきたときには書いていた行を見失う |
| WU-26 | 一覧は **Radix Themes の `Table`** で、1行に1件。列は選択・本体・1件のコピーの3つで、選択の列の見出しに全選択を置く。本体の1段目に表示名とスペース管理者の印、2段目にログイン ID と**メールアドレス**（チームはチーム ID と人数）を並べる。**メールアドレスは表示と絞り込みにだけ使い、コピーには入れない**（WU-23） | 人を見分ける手掛かりが表示名しか無いと、同姓同名や表示名を変えた人を取り違える。メールアドレスは管理者が Backlog の画面で見ているものと同じで、V-B4 がログイン ID の代わりに書かれやすいと見ている値でもあるので、探す側に置けば写し間違いの元を画面の中で解消できる。**`CheckboxCards` を採らない**のは、カード全体が1つのボタンで中に1件のコピー（WU-24）を置けないため。`Table` なら選べる表の見慣れた形になり、全選択を別の行に持たずに済む |

### 2.7 Export ページ

[EX-20](export.md#ex-20-web-ui-に載せ別のページに置く) で `export` を Web に載せると決めた。
その画面の形をここで決める。

| ID | 決定 | 理由 |
| --- | --- | --- |
| WU-27 | `export` は **Apply とは別のページ**に置く。ヘッダーに Apply / Export のタブを置き、行き先は `#/` と `#/export`（WU-1） | 1回の来訪で export と apply を両方やることはまれである。書き出したものを使い回すには `key` と `name` を書き換える必要があり（EX-3）、それはファイルをリポジトリに置いて手で直す作業で、その場で apply する流れにならない。同じページに段を足すと、ステッパーが「接続 → 書く → 計画 → 適用」の一本道でなくなる |
| WU-28 | Connect の段は**1つだけ**で、両ページの先頭に同じものを出す。接続・一覧のペイン（§2.6）・各ページの入力と結果は**ページを切り替えても保持する**。見えないページは非表示にするだけで、アンマウントしない | 接続し直させると API キーを2度打たせることになる。API キーの欄は制御できない（§2.4）ので、ページごとに欄を持つと片方は空に見えたまま接続だけが生きる形になる。**アンマウントしないのは、apply の実行中に Export を開いただけで進捗と離脱の警告が消えるため**で、WU-18 が段ごとに境界を置いたのと同じ懸念である |
| WU-29 | 入力はプロジェクトキー1つと Export ボタン（WU-15 の Action）。キーの形は Web で判定しない | 判定は GET を出す `createExport` が持つ（EX-3）。Web でも判定すると、同じ規則が2か所に書かれる（NFR-6） |
| WU-30 | 結果は読み取り専用の等幅表示で出し、**Copy** と **Download**（`<KEY>.yaml`）を置く。課題件数の案内は `renderExportNotes` の文面をそのまま出す。止まったときは診断だけを出し、Yaml は出さない | Download は CLI の `> projects/PROJ_A.yaml`（CL-8）に当たる。案内の文面を Web で書き直さないのは NFR-6。止まったときに何も出さないのは EX-17 と同じ理由で、半端な Yaml を写させない |
| WU-31 | 書き出した Yaml を **Apply ページのエディタへ送る導線を持たない** | EX-20 が未決にしていた「読み込んだ結果でエディタを上書きすることと WU-3 の関係」を、関係が生まれない形で閉じる。送れば書きかけのマニフェストを黙って上書きしうるうえ、そのまま Plan を押すと書き出し元（課題を持ちうる）を指したまま V-B3 で止まる。使い回すには `key` と `name` を変える必要があるので、コピーして貼る一手間は余計な手順ではない |
| WU-32 | 結果は**接続の印**（WU-3）に紐づけ、接続が変われば捨てる。キーの欄を書き換えても捨てず、結果にはどのキーを書き出したものかを出す | 別のスペースに繋ぎ直した後に前のスペースの Yaml が残ると、どこから書き出したかが画面から読めない（WU-22 と同じ線引き）。キーは結果に載っているので、欄を書き換えても取り違えは起きない。打ち直すたびに消すと、次のキーを打ち終えるまで手元の結果が読めなくなる |

```
┌ backlog-blueprint ─────── [Apply] [Export] ─── [👤 Users] [👥 Teams] ┐
│ ① Connect ── ② Export                                                │
│ ┌ 1 Connect ─────────────────────────────────────┐                   │
│ │ ...（Apply ページと同じ段）                    │                   │
│ └────────────────────────────────────────────────┘                   │
│ ┌ 2 Export ──────────────────────────────────────┐                   │
│ │ Project key [ PROJ_A           ]    [ Export ] │                   │
│ │ NOTE  PROJ_A holds 3 issues, so plan and ...   │                   │
│ │ PROJ_A.yaml             [ Copy ] [ Download ]  │                   │
│ │ # yaml-language-server: $schema=...            │                   │
│ │ key: PROJ_A                                    │                   │
│ └────────────────────────────────────────────────┘                   │
```

## 3. 判断理由のまとめ

| ID | 決定 | 採らなかった案と理由 |
| --- | --- | --- |
| CL-1 | `validate` を足す | `plan --offline`。語義矛盾で、plan の約束を果たせない |
| CL-2 | API キーは環境変数のみ | `--api-key`。`ps` とシェル履歴とコマンドログに残る |
| CL-3 | `-f` は1回だけ | 複数ファイル。プロジェクト境界をまたぐ部分適用が生まれ、中断レポートが複雑になる |
| CL-4 | 既定で確認プロンプト | 確認なしで即実行。破壊的操作に対する最後の砦が無くなる |
| CL-5 | `yes` の全文入力 | `y` 1文字。Enter 連打で通る |
| CL-6 | 非 TTY では確認なしだとエラー | 非 TTY では自動承認。CI で気付かず適用されるのが最悪 |
| CL-7 | `export` は位置引数1つ | `-f` に揃える（対象は修飾子ではなく主語）／`-o` で出力先を受ける（リダイレクトと二重）／`-f` で既存 Yaml を書き戻す（差分取り込みの導線になる） |
| CL-8 | stdout は Yaml だけ | 案内も stdout に混ぜる。`> file` がそのまま壊れる |
| CL-9 | 終了コードは 0 / 1 | `plan` に揃えて 2 を持つ。対応する状態が `export` に無い |
| — | 削除を含むときだけ確認、は採らない | 「いつ止まるか」がマニフェスト次第になり、挙動が非決定的に見える |
| WU-1 | URL はページだけをハッシュで表す | ステップごとの URL。状態がメモリのみなので復元できず、URL が嘘になる／ルーターのライブラリ。行き先2つに対して `hashchange` の購読以上の仕事が無い／履歴 API の path。GitHub Pages に SPA フォールバックが要る |
| WU-3 | 入力変更で計画を破棄 | 古い計画のまま apply を許す。「plan で見たものが apply される」が壊れる |
| WU-15 | 非同期は Action に任せる | 保留中の真偽値を自前で持つ。倒し忘れた経路が押しっぱなしの画面になる |
| WU-15 | Action は `startTransition` から呼ぶ | `<form action>`。React が Action の後にフォームを reset し、非制御の API キー欄が空になる |
| WU-16 | 検証は後回しの描画 | 固定の待ち時間。速く打つ人には長く、重い入力には短い数字を1つ選ぶことにしかならない |
| WU-17 | 実行中かどうかは記録から導く | 真偽値で別に持つ。進捗の最後の1件と「終わった」が別々の描画に乗る |
| WU-18 | 例外は段ごとに受け止め、中身は出さない | 1枚で全体を覆う。apply の最中に落ちると進捗も離脱の警告も消える |
| WU-19 | React Compiler を入れ、畳めなければ落とす | 既定の素通し。外れても画面は動くので、遅くなったことに気付けない |
| WU-20 | 一覧は非モーダルのサイドペインで1枚ずつ | モーダル。一覧から写しながらエディタに貼れない／2枚同時。本文の幅を2枚分削る |
| WU-21 | 接続できるまで一覧を開けない | 接続前から開ける。送信層が無く、スペース管理者でない人には写した値の行き先が無い |
| WU-22 | 初めて開いたときに取得し、閉じても保持する | 開くたびに取得。選択が消え、読み取りの枠も減る／接続時に先回りで取得。開かない人の枠まで使う |
| WU-23 | 段付きの Yaml の系列を core で書き出す | 名前を改行で並べるだけ。段と引用と EX-5 のエスケープを利用者に任せることになる |
| WU-24 | 1件ずつのコピーボタンも置く | チェックボックスだけ。1件のために選択の付け外しが要り、外し忘れが次のコピーに紛れる |
| WU-25 | ヘッダーを上端に留める | 先頭にだけ置く。一覧を開くたびにスクロールで戻ることになる |
| WU-26 | 一覧は `Table`、メールアドレスは表示と絞り込みだけ | `CheckboxCards`。1件のコピーを中に置けない／メールアドレスもコピーする。雛形とリポジトリに個人情報が広まる |
| WU-27 | export は別ページ | Apply の段に足す。一本道のステッパーが崩れ、同時に使うことがまれな2つの流れが1画面に並ぶ |
| WU-28 | Connect は1つ、ページは隠すだけ | ページごとに接続させる。API キーを2度打たせる／切り替えでアンマウントする。apply の最中に進捗と離脱の警告が消える |
| WU-29 | キーの形は core が判定 | Web でも判定する。規則が2か所に書かれる |
| WU-30 | Copy と Download、止まれば何も出さない | エラーがあっても書けた分を出す。半端な Yaml が写される |
| WU-31 | Apply のエディタへ送らない | 送るボタンを置く。書きかけを上書きし、書き出し元を指したまま V-B3 で止まる流れを作る |
| WU-32 | 結果は接続の印に紐づけ、キーの欄には紐づけない | キーの欄にも紐づける。打ち直すあいだ手元の結果が読めなくなる |
