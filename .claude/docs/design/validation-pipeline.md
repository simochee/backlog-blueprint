# 検証パイプライン

最終更新: 2026-09-20
前提: [要件定義 §5 検証仕様](../requirements/requirements-definition.md#5-検証仕様) / [マニフェストのスキーマ定義](manifest-schema.md) / [core のデータモデル](core-reconciler.md)

要件定義 §5 が定めた V-A* / V-B* を、**どこで・どの順に走らせるか**まで落とす。

## 1. 分類の軸が2つある

要件定義 §5 の「静的検証（5.1）」「スペース検証（5.2）」は、
**何を根拠に判定するか**で切られている。設計に必要なのは**いつ走らせるか**で、この2つは一致しない。

| 検証 | 要件定義の分類 | 実際に必要なもの |
| --- | --- | --- |
| V-A6 既定ステータスを含む | 静的 | **スナップショット。** 既定かどうかは ID 1〜4 で判定すると決まっており、名前では判定しない |
| V-A15 記述順と表示順の一致 | 静的 | **計画結果。** 既存要素が何件あるかで適用後の並びが変わる |
| V-A16 チーム経由の重複記述 | 静的 | **スペースのチーム所属情報** |
| V-B7 振替先が決定できる | スペース | **計画結果。** 削除対象が確定していないと判定できない |
| V-B8 レート制限の残量 | スペース | **計画結果。** 操作数が確定していないと比較できない |

そこで**実行ステージ**という軸を足す。要件定義の ID と分類はそのまま維持する
（ID はエラーメッセージと受け入れ基準に出る安定した識別子なので、付け替えない）。

## 2. ステージ

| ID | ステージ | ネットワーク | 入力 |
| --- | --- | --- | --- |
| S1 | 構文 | 無し | Yaml のテキスト |
| S2 | 展開 | 無し | S1 のドキュメント + 環境変数 |
| S3 | スキーマ | 無し | S2 の値 |
| S4 | 静的意味 | 無し | S3 を通ったマニフェスト |
| S5 | 接続・権限 | GET | API キー、スペースドメイン |
| S6 | スナップショット | GET | S4 のマニフェスト + 空間の実状 |
| S7 | 計画 | 無し | S6 のスナップショット + 算出された `Action[]` |

S7 がネットワークを使わないのは、`plan()` が純粋関数だから（[C-2](core-reconciler.md#c-2-plan-は純粋関数ネットワークにアクセスしない)）。
計画を作ってから判定する検証は、追加の GET を一切必要としない。

### 2.1 ゲートの方針

| 決定 | 内容 |
| --- | --- |
| VG-1 | **ステージ内は全件検出して列挙する。** 1件目で止めない（FR-2.3） |
| VG-2 | **ステージ間はゲートにする。** 前のステージにエラーが1件でもあれば次へ進まない |
| VG-3 | 例外: S2 の未解決 `${ENV}` は、番兵の値を入れて S3・S4 まで進める |

VG-2 の理由。前のステージが失敗しているとき、後のステージの結果は意味を持たない。
スキーマに通らないマニフェストで「課題種別が0件です」と言っても、
それが本当の誤りなのかパースの副作用なのか利用者に判断できない。
ネットワークを使うステージではさらに、壊れたマニフェストでレート制限を消費することになる。

VG-3 の理由。環境変数を1つ直すたびに次の未定義が出るループは FR-2.3 が避けようとしているものそのもので、
それはステージをまたいでも同じ。番兵を入れれば「環境変数が2つ足りない」と
「`statuses` に既定が足りない」を一度に出せる。番兵は型検証を通る不透明な文字列とし、
比較・長さ・パターンの判定には使われない値にする。

## 3. ステージと検証の対応

### S1 構文

Yaml のパース。失敗したら位置付きで報告して終了。
解釈規則は [Y-1〜Y-5](manifest-schema.md#2-yaml-の解釈規則)。

| 検証 | 内容 | 結果 |
| --- | --- | --- |
| V-A23 | Yaml として妥当である | エラー |
| [Y-5](manifest-schema.md#2-yaml-の解釈規則) | 複数ドキュメント（`---` 区切り）でない | エラー |

### S2 展開

| 検証 | 内容 | 結果 |
| --- | --- | --- |
| V-A4 | `${ENV}` がすべて解決できる | エラー（`validate` では警告 → §4） |

解決できた値は `Secret` になる（[E-4](manifest-schema.md#3-env-展開)）。

### S3 スキーマ

生成された JSON Schema による検証。表現できる範囲は
[マニフェストのスキーマ定義](manifest-schema.md) の通り。

| 検証 | 表現方法 |
| --- | --- |
| V-A1 未知キー | `additionalProperties: false` |
| V-A2 必須キー（`key` / `name`） | `required` |
| V-A3 プロジェクトキーの形式 | `pattern` |
| V-A7 ステータス総数 12 以下 | `maxItems: 12` |
| V-A11 カスタム属性の型別必須パラメータ | `allOf` + `if`/`then` |
| V-A13 `access` 各リスト内の重複 | `uniqueItems: true` |
| V-A18 色が文字列である | `type: string` + Y-3 による専用メッセージ |
| V-A8 ステータスの色が10色パレット内 | `statuses[].color` の `enum` |
| V-A21 上記以外のすべての型・制約違反 | `type` / `enum` / `minLength` / `minimum` / `pattern` |

V-A21 は受け皿である。スキーマが表現する制約のうち要件定義が個別に ID を振っているのは一部だけで、
`settings.textFormattingRule` の enum、`name` の `minLength`、`milestones[].startDate` の日付パターン、
課題種別の色の enum（[K-4](manifest-schema.md#k-4-課題種別の色は-enum-としパレット外はエラーにする)）などは
対応する ID を持たない。`Diagnostic.id` は必須（[§5](#5-診断diagnostic-の形)）なので、
これらをまとめて V-A21 として報告する。

**個別の ID があるものが V-A21 に落ちてはならない。** V-A21 が出ることは
「スキーマには違反しているが、要件定義が名前を付けていない誤り」を意味し、
頻出するなら ID を新設する合図になる。

V-A18 は、引用符の付け忘れで `color: null` になった場合に
「引用符で囲んでください」という固有のメッセージを出す。
単なる型エラー（`expected string, got null`）では原因にたどり着けない。

### S4 静的意味

スキーマで表現できない、マニフェスト内で閉じた検証。

| 検証 | 内容 | 結果 |
| --- | --- | --- |
| V-A5 | 各リソース内で `name` が重複していない | エラー |
| V-A9 | `issueTypes` が1件以上ある | エラー |
| V-A10 | `customFields[].applicableIssueTypes` が `issueTypes` の `name` を指す | エラー |
| V-A17 | `oldname` が同一リソース内の他要素の `name` と衝突しない | エラー |
| V-A19 | マイルストーンの `startDate` ≤ `releaseDueDate` | エラー |
| V-A20 | カスタム属性の `min` ≤ `max` | エラー |
| V-A22 | 各リソースの `name` / `oldname` に `}` を含まない | エラー |
| V-A24 | `webhooks[].events` の数値が既知の activityTypeId である | 警告 |
| V-A25 | 同定名に `${ENV}` を使っていない | 警告 |

V-A25 は、マスクできない場所に秘匿値を書いたことを利用者に知らせる
（[E-7](manifest-schema.md#e-7-同定名は-secret-にできない)）。同定名は解決表のキーと
`Action.id` を兼ねるため構造的に `Secret` にできず、`--output json` と text の両方に平文で出る。
エラーにしないのは、プロジェクト名やカテゴリー名を環境ごとに変える運用が普通にありうるため。
判定に要るのは S2 が返す展開経路の集合だけなので S4 に置く。

V-A24 は W-4 後半（未知の数値は警告）の置き場所である。S3 は前方互換のため数値を無条件に通すので
（[K-7 の `events` の型](manifest-schema.md#11-webhooks)）、既知の一覧に無い数値をここで拾う。
**警告なので適用は止まらない。** Backlog が新しいイベントを追加したときに CLI を更新せず使える、
という W-1 の目的をそのまま残す。

**V-A12 は S4 に置けない。** `subtaskingEnabled` を省略した場合、K-3 により現状維持となるが、
S4 はスナップショットを持たないため現状が真かを知る手段がない。V-A6 / V-A8 / V-A14 が
「判定にスナップショットが要る」という理由で S6 に置かれているのと同じ事情なので、S6 に移す。

V-A19 / V-A20 は設計フェーズで提案し、**採用が確定した**（要件定義 §5.1 に採番済み）。
どちらも API に投げれば拒否されるが、S4 で止めれば「適用を始めてから気付く」を1つ減らせる
（R-2 の趣旨）。判定はマニフェストだけででき、**利用者が自分で直せる誤り**である点が採用の決め手。
未採用とした V-C1 が「ツール自身のバグを捕まえる網」で利用者に直しようがないのとは、
性質が逆になる。

V-A22 はツール側の都合による制約である。`HttpRequest.path` に埋め込む未解決参照の記法が
`{$ref:<kind>:<name>}`（[plan-output §2.1](plan-output.md#21-構造)）で、名前の終端を `}` で
判断するため、名前自体に `}` があると往復できない。

**トップレベルの `name`（プロジェクト名）は対象外。** プロジェクトが `Ref` で参照されるときのキーは
`key`（`^[A-Z0-9_]+$`）であり、プロジェクト名が `{$ref:...}` に入る経路が無い。
記法の都合で狭めてよいのは、記法に載る名前だけである。

Backlog 側では `}` を含む名前を付けられるので、**これはツールが利用者を狭めている箇所**である。
`hint` にもそう書く。記法にエスケープを足す案は、JSON 出力の読みやすさを
PO-3 の利点（そのまま監査・不具合報告に使える）ごと損なうため採らない。

### S5 接続・権限

| 検証 | API | 結果 |
| --- | --- | --- |
| V-B1 | `GET /users/myself` が成功する | エラー |
| V-B2 | `roleType` が 1（スペース管理者）である | エラー |

このステージを独立させるのは、**以後のすべての GET が無駄になる条件**だから。
権限が無いと分かった時点で、スナップショットの取得を始める理由がない。

### S6 スナップショット

各 reconciler の `read()` を実行したうえで判定する。

| 検証 | 内容 | 必要な取得 | 結果 |
| --- | --- | --- | --- |
| V-B3 | 対象プロジェクトの課題件数が0（**確認できた**うえで0） | `GET /projects/:key` → `GET /issues/count` | エラー |
| V-B4 | `access` のユーザー ID がスペースに存在する | `GET /users` | エラー |
| V-B5 | `access` のチーム名がスペースに存在する | `GET /teams` | エラー |
| V-B11 | `access.administrators` にスペース管理者（`roleType` が 1）が含まれていない | `GET /users` | エラー |
| V-A6 | 既定ステータス（ID 1〜4）の名前がすべて `statuses` に含まれる。**既存プロジェクトはスナップショットの ID 1〜4、未作成は[日英2組の表](../research/backlog-api-constraints.md#既定リソースの表示名)で判定する**（どちらの組に一致しても通す） | `GET /projects/:key/statuses` | エラー |
| V-A6a | 既定ステータスに `color` / `oldname` が無い | 同上 | エラー |
| V-A26 | カスタムステータス（既定の ID 1〜4 以外）に `color` が指定されている | 同上 | エラー |
| V-A14 | ステータスの並びが API の順序制約を満たす | 同上 | エラー |
| V-A12 | `grandchildIssueEnabled` が真なら `subtaskingEnabled` も真。省略時は現状の値で判定し、**プロジェクトが未作成なら現状が無いのでエラー** | `GET /projects/:key` | エラー |

**V-B11 は実 API でしか分からなかった制約である。** スペース管理者はプロジェクト管理者に
なれない（`Only normal-user role can be a project administrator.`）。実行者は必ず
スペース管理者なので（FR-5.4）、**実行者を `administrators` に書くと必ず失敗する**。
判定に要るのは `GET /users` が返す `roleType` だけなので S6 に置く。

`hint` では `members` に書く道を案内する。スペース管理者はプロジェクトに個人参加でき、
参加していなくてもスペース管理者としてそのプロジェクトを操作できる。

**V-B10 は撤回した。** `applicableIssueTypes` の絞りは
`applicableIssueTypes[]=`（空の値を1つ）を送れば解除できることを実測で確認したため
（[リクエストの形式](../research/backlog-api-constraints.md#空配列を送る方法)）。
送信できないものを計画させないためのゲートとして新設したが、送信できるので要らない。
`qs` が空配列をキーごと落とすことへの対応は送信層が持つ。
**トランスポートの都合を仕様に持ち込まずに済んだ。**

**V-A8 だけは S3 に置く。** 「既定かどうかは ID で判定する」という制約は V-A8 には効かない。
V-A6a が既定ステータスに `color` を書くこと自体を禁じているので、**マニフェストに書ける `color` は
カスタムステータスのものに限られる**。つまり「すべての `statuses[].color` がパレット内」と
「カスタムステータスの色がパレット内」は同じことを言っている。

スキーマの enum で判定すれば、エディタにも10色の補完が出る（M-1）。S6 に置くと
「CLI では落ちるのにエディタは黙っている」が生まれ、M-1 が消したかった食い違いが戻る。
そのぶん、**既定ステータスに実際の既定色（パレット外）を書いた場合は V-A6a ではなく V-A8 が出る**。
どちらも「既定に色を書くな」という同じ誤りを指しているので、実害は無い。

**V-A26 は V-A6a の裏である。** `POST /projects/:key/statuses` は `color` を必須パラメータに取る
ので、カスタムステータスには色が要る。一方 V-A6a は既定に色を書くことを禁じている。
**S3 ではどちらか判定できない**（K-5。既定かどうかは ID ＝ スナップショットが要る）ため、
スキーマの `required` には入れられず、ここに置くしかない。
V-A6（既定4つを含む）/ V-A6a（既定に色を書くな）/ V-A26（カスタムには色が要る）で1組になる。

**既に Backlog 側にあるカスタムステータスにも色を要求する。** `PATCH` は `color` を必須に
取らないので、K-3（省略されたスカラーキーは現状維持）だけを見れば省略を許せる。それでも
要求するのは、**同じマニフェストがプロジェクトの有無で通ったり落ちたりするのを避ける**ため。
省略を許すと、既存プロジェクトに当てて動いたマニフェストが、新規プロジェクトに当てた途端
API に拒否される。UC-2（GUI で作ったプロジェクトを Yaml 管理に乗せ換える）は、
同じ Yaml を別の場面でも使えることを前提にしている。

**V-A6 / V-A6a / V-A14 がここに来る理由。**
[API 制約](../research/backlog-api-constraints.md#ステータス) が
「既定ステータスは ID で判定する。名前の一致では判定しない」と決めている。
ID はスナップショットにしか無い。名前で判定する実装に寄せれば S3 に前倒しできるが、
それは確定済みの調査結果に反する。

副次的に、既定ステータスの表示名がスペースの言語設定で変わってもツールは正しく動く。
**既存プロジェクトでは `GET /projects/:key/statuses` が実際の表示名を返すので、名前の出どころに迷いはない。**

**新規プロジェクトだけは、まだ存在しないので取得できない。** ID が 1〜4 の固定値であることは
分かっていても、表示名はスペースの言語設定に依存する。ここは
[既定ステータスの表示名](../research/backlog-api-constraints.md#ステータス)として
**日本語と英語の2組をツールが持ち、どちらかに一致すれば V-A6 を満たしたとみなす**。

同じスペースの他プロジェクトから引く案は採らない。`GET` が1〜2件増えるうえ、
スペースに他プロジェクトが1つも無い場合に判定できる根拠が無くなる。
2組を持つ方式なら、Backlog が対応言語を増やしたときだけ追随すればよい。

### S7 計画

`Action[]` が算出された後。ネットワークを使わない。

| 検証 | 内容 | 結果 |
| --- | --- | --- |
| V-B6 | 実行者自身がプロジェクト管理者から外れる計画になっていない | エラー |
| V-B7 | 削除 Action の振替先が、削除対象自身ではない | エラー |
| V-A15 | 記述順と適用後の表示順が一致する | 警告 |
| V-A16 | `access.members` にチーム経由の参加者が書かれていない | 警告 |
| V-B8 | 更新系レート制限の残量が計画の操作数以上ある | 警告 |

V-C1（すべての `Ref` が実行時点で解決可能であることのシミュレーション）は**未採用**。
経緯は [core のデータモデル §3.4](core-reconciler.md#34-v-c1-参照解決シミュレーション未採用)。

V-A16 はチームの所属ユーザーを知る必要があるが、`GET /api/v2/teams` が
各チームの `members[]` を返すことを**実測で確認済み**（2026-09-19）。
プロジェクトにまだ参加していないチームについても所属者が分かるので、
新規追加するチームを含めて判定できる。

## 4. コマンドごとのステージ構成

| | S1 構文 | S2 展開 | S3 スキーマ | S4 静的意味 | S5 権限 | S6 スナップショット | S7 計画 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `validate` | ✓ | ✓＊ | ✓ | ✓ | — | — | — |
| `plan` | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| `apply` | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ → 確認 → 実行 |
| Web Step 1 | — | — | — | — | ✓ | — | — |
| Web Step 2 | ✓ | ✓＊＊ | ✓ | ✓ | — | — | — |
| Web Step 3 | — | — | — | — | （再実行） | ✓ | ✓ |

Web Step 3 の S5 が「済」ではなく「再実行」なのは、計画の算出が S5 から S7 までを
1本の経路として持っているためである（core の `buildPlan`）。Step 1 で判定済みでも
`GET /users/myself` が1回余分に飛ぶ。**読み取り1回の無駄で、権限が途中で変わった場合に
気づけるという利点もある**ので、経路を分解してまで避けない。

### VP-1: `validate` では V-A4 を警告に下げる（＊）

| 決定 | 内容 |
| --- | --- |
| VP-1 | `validate` において、未解決の `${ENV}` はエラーではなく警告とする |

`validate` の目的は「マニフェストの**書き方**が正しいか」であって
「**この環境で**実行できるか」ではない。後者は `plan` の仕事。
秘匿値を持たない PR チェックで回せることが `validate` を足した理由のひとつ（CL-1）なので、
ここでエラーにすると足した意味が半分消える。

保たれる不変条件は一方向になる。

- **`validate` がエラーなら `plan` も必ずエラーになる**（CI の速いゲートとして使える）
- 逆は成り立たない（`validate` が通っても `plan` は環境変数不足で落ちうる）

CI で使うときに欲しいのは前者の向きなので、これで足りる。

### Web UI での V-A4（＊＊）

環境変数が存在しないので、`${NAME}` ごとに生成した入力欄が空かどうかで判定する
（[Web UI Step 2](cli-and-web-ui.md#step-2-manifest)）。
メッセージは「環境変数が未定義」ではなく「値が未入力」になる。

### Web UI で S5 が先に来ることについて

CLI では S5（権限）が S1〜S4 の後だが、Web では Step 1 で先に判定する。
矛盾ではなく、**入力が揃う順序が違う**だけ。
CLI は起動時点で環境変数もファイルも揃っているが、
Web は画面に入力されるまで何も無い。

順序を CLI に合わせて「マニフェストを書き終えてから権限エラー」にする案は採らない。
書き終えた後で「そもそも権限がありません」は、利用者の時間を最も無駄にする順序。

## 5. 診断（Diagnostic）の形

すべてのステージが同じ構造を返す。

```ts
type Diagnostic = {
  id: string                     // "V-A6"。要件定義の ID をそのまま使う
  severity: 'error' | 'warning'
  stage: 'syntax' | 'expand' | 'schema' | 'semantic' | 'auth' | 'snapshot' | 'plan'
  path: string                   // "statuses/2/color"
  line?: number                  // S1〜S4 のみ。Yaml 上の位置
  column?: number
  message: string                // 何がダメか（英語）
  hint?: string                  // どう直すか（FR-2.2）
}
```

| 規則 | 内容 |
| --- | --- |
| DG-1 | `message` と `hint` は英語のみ（NFR-9）。利用者が付けたリソース名はそのまま埋め込む |
| DG-2 | `hint` は「どう直すか」を書く。直しようが無い警告（V-A15）では「なぜそうなるか」を書く |
| DG-3 | 出力順は ステージ順 → `line` 順。利用者がファイルを上から追える |
| DG-4 | `path` は JSON Pointer 風のスラッシュ区切り。配列は添字 |
| DG-5 | 位置情報を持てるのは S1〜S4 のみ。S5〜S7 は `path` だけ |

出力例（要件定義 §5.3 の形式）。

```
2 validation errors. Nothing has been applied.

ERROR [V-A6] statuses: default statuses cannot be deleted
  missing default status: 処理済み
  → add "処理済み" to statuses, or rename it with oldname

ERROR [V-B3] key: project already has issues
  PROJ_A: 43 issues
  → only projects with zero issues can be targeted
```

## 6. なぜ検証を7段に割るのか

要件定義 R-2 —— *「消せないもの・0件にできないものが定義上0件になるなら、最初の検証で指摘して中断する。
実行を始めてから気付くのは許容しない」* —— を満たす構造は、突き詰めると1つしかない。

**適用を1件でも始める前に、計画を完成させ、計画に対して検証を走らせること。**

これは「検証 → 計画 → 適用」ではなく「検証 → 計画 → **計画の検証** → 適用」の4段になる。
S7 がその「計画の検証」にあたる。V-B6 / V-B7 / V-B8 が
すべて計画を必要とするのは偶然ではなく、R-2 が要求している検証の性質による。

要件定義 §6 の適用順序表がフェーズ0を「検証」としているのは、
この S1〜S7 の全体を指している。

## 7. 適用対象の限定

本ツールは差分適用も継続同期もしない（[要求設計 §6](../requirements/requirement-design.md#6-スコープ)）。
対象は**新規作成するプロジェクト**と**まだ何も始まっていない既存プロジェクト**の2つだけである。

この限定は文書上の宣言では守れない。検証で担保する必要がある。
`reconciler` や「差分算出」という語を使っているため Terraform 的な継続同期ツールに見えるが、
**本ツールは一度きりの初期化ツールであり、稼働中のプロジェクトに当てる想定が無い。**

### 7.1 なぜ課題以外のリソースで問題になるか

すべてのリソースで「Yaml に書いていないものは削除」する（要件定義 §2.2）。
`access` も例外ではない。稼働中のプロジェクトに当てると、
**Yaml に名前が無い参加者が全員削除される。**

課題の削除は V-B3 が防いでいるが、メンバーの削除は防いでいない。
課題種別やステータスの削除は振替先があるので復旧の余地があるのに対し、
メンバーの削除は人をプロジェクトから締め出す操作で、気付くのは締め出された側になる。

### 7.2 現状のゲートとその穴

| 観点 | 実測の結果 |
| --- | --- |
| `GET /issues/count` が数える範囲 | **完了済みを含む全件**（実測）。完了1万件のプロジェクトが「0件」に見える穴は**無い** |
| 課題0件は「空」を意味するか | **意味しない。** Git 専用プロジェクト（課題を使わずリポジトリだけ使う）、Wiki・ドキュメント置き場のプロジェクトは、稼働していても課題0件のまま |

つまり V-B3 は**課題を守るゲートであって、プロジェクトが空であることのゲートではない**。

### VP-5: V-B3 は fail-closed にする

| 決定 | 内容 |
| --- | --- |
| VP-5 | 課題件数を**確認できなかった**場合もエラーとして扱い、適用に進まない |

権限不足・ネットワーク断・API 変更のいずれでも「確認できなかった」は起こりうる。
唯一のゲートが開いたまま破壊的操作に進むことになるので、
**確認できたうえで0件のときだけ通す**と明示する。

「取得に失敗したので判定をスキップする」という実装を許さないために、
スナップショットの型は課題件数を `number` として持ち、`number | undefined` にしない。

### V-B9 初期状態であることの確認（未採用）

課題0件に加えて、プロジェクトが実際に始まっていないことを確認する。

| ID | 検証内容 | 推奨する結果 |
| --- | --- | --- |
| V-B9a | Wiki が0件 | エラー |
| V-B9b | Git リポジトリが0件、または全リポジトリが未 push（`pushedAt` が null） | エラー |
| V-B9c | 共有ファイルが0件 | エラー |
| V-B9d | 参加者が実行者のみ | 警告 |

V-B9d だけ警告にするのは、立ち上げ準備としてメンバーを先に入れておく運用が普通にあるため。
一方 Wiki・Git・共有ファイルが存在するプロジェクトは、課題を使っていないだけで
**すでに使われている**と判断してよい。

これは要求設計 R-4（課題0件なら実行可）を**狭める**変更にあたるため依頼者の判断を仰ぎ、
**未採用と決まった**。R-4 をそのまま維持し、適用対象のゲートは V-B3（課題0件）だけとする。
上の表は再検討する場合の出発点として残す。

したがって §7.2 が指摘した穴 —— 課題0件でも Wiki・Git・共有ファイルで稼働している
プロジェクトがありうる —— は**塞がないまま残る**。V-B3 は課題を守るゲートであって、
プロジェクトが空であることのゲートではない。

> `要検証` — `settings.useGit: true` でプロジェクトを作ったとき、
> Git リポジトリが自動作成されるか。V-B9 を再検討するときにだけ必要になる。
> 自動作成されるなら V-B9b は「0件」ではなく「未 push」を条件にしなければ UC-2 を壊す。

### 7.3 中断後の再開は保証されない

apply が中断したあと、再実行までの間に誰かが課題を1件でも作ると、
V-B3 で止まって**再開できなくなる**。

これは仕様として正しい（課題があるプロジェクトには当てない）が、
中断レポートの案内文は無条件に「もう一度実行すれば続きから進む」と言ってはいけない
（[plan の出力仕様 §3.2](plan-output.md#32-中断時fr-44)）。

## 8. 判断理由のまとめ

| ID | 決定 | 採らなかった案と理由 |
| --- | --- | --- |
| — | 実行ステージという軸を足す | 要件定義の 5.1 / 5.2 の分類を書き換える。ID がエラーメッセージと受け入れ基準に出ており、付け替えると追跡できなくなる |
| VG-1 | ステージ内は全件列挙 | 1件目で止める。直して再実行するたび次が出るループ（FR-2.3） |
| VG-2 | ステージ間はゲート | 全ステージを常に走らせる。壊れたマニフェストでレート制限を消費し、原因不明の二次エラーが混ざる |
| VG-3 | 未解決 `${ENV}` は番兵で先へ進める | S2 で止める。環境変数を1つずつ直すループになる |
| — | V-A6 / A6a / A14 を S6 に置く | 既定ステータスを名前で判定して S3 に前倒し。確定済みの調査結果（ID で判定する）に反し、言語設定の違うスペースで壊れる |
| — | V-A8（色）だけ S3 に置く | S6 に揃える。エディタに10色の補完が出ず、「CLI では落ちるのにエディタは黙っている」が生まれる |
| VP-5 | V-B3 を fail-closed にする | 確認できなければ判定をスキップして続行。唯一のゲートが開いたまま破壊的操作に進む |
| VP-1 | `validate` では V-A4 を警告 | エラーのまま。秘匿値を持たない CI で回せず、`validate` を足した理由が半分消える |
| V-A19 / V-A20 | 採用し、S4 に置く | 見送る。利用者が直せる誤りを API のエラーまで持ち越すことになり、R-2 の趣旨から外れる |
| V-C1 | **未採用** | S7 に置く。`Ref` の解決可能性は V-A10 の静的検証に委ね、漏れた場合は実行時エラーとして現れる |
| V-B9 | **未採用** | 採用して R-4 を狭める。GUI で作った直後のプロジェクトを通すという UC-2 の前提に例外を作ることになる |
| — | Web では S5 を最初に置く | CLI と同じ順序。書き終えてから権限エラーは最も時間を無駄にする |
