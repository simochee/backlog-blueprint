# backlog-blueprint

> この文書は [README.md](README.md) の日本語訳です。内容が食い違うときは英語版が正です。

[Backlog](https://backlog.com/ja/) のプロジェクト設定を YAML ファイルに宣言し、そこからプロジェクトを作成します。
マニフェストはリポジトリに置くので、プロジェクトの形をプルリクエストでレビューし、次のプロジェクトに写し、
人が手で追う手順書の代わりに組織のテンプレートとして持っておけます。

```
projects/PROJ_A.yaml  ──[ validate ]──[ plan ]──[ apply ]──▶  Backlog space
```

扱うのは、プロジェクトの基本設定、課題種別、状態、カテゴリー、マイルストーン、カスタム属性、チーム・メンバー・
管理者、Webhook です。

## このツールがしないこと

backlog-blueprint は**一度きりの初期化ツール**です。プロジェクトを一度セットアップするためのもので、
Backlog をファイルと継続的に一致させ続ける仕組みではありません。導入の前に知っておくべき帰結が2つあります。

- **課題が1件もないプロジェクトにしか触れません。** プロジェクトが既に存在し、課題が1件でもあれば、`plan` と
  `apply` は何も変更する前に止まります。運用中のプロジェクトは対象外で、この確認を外す方法はありません。
- **状態を持ちません。** state ファイルもドリフト検知もありません。毎回スペースの現在の状態を読み、
  マニフェストだけから何をするかを計算します。`export` はプロジェクトの*今の*姿をテンプレートの出発点として
  書き出すもので、ドリフトを見張る手段ではありません。このツールが2つのマニフェストを比べることもありません。

内部の設計文書はリソースごとのモジュールを *reconciler* と呼び、`plan` / `apply` は Terraform を使ったことがある人には
見慣れたものでしょう。借りているのは言葉だけです。`apply` が終わった後にプロジェクトを見張るものは何もありません。

次のものも意図的に対象外です。

- YAML のフォーム型エディタ
- Git リポジトリ（Backlog API では作成できません）
- 課題と Wiki の内容
- スペースの設定
- プロジェクトの削除とアーカイブ

## 始める前に

- Backlog のスペースと API キーが必要です。**プロジェクトの作成、状態の変更、プロジェクト管理者の指名には
  スペース管理者のキーが必要です。** Backlog がそれ以外を受け付けないためです。既に存在するプロジェクトに
  それ以外を適用するだけなら、プロジェクト管理者のキーで足ります。先にプロジェクトを作っておくか、状態を
  今のままにしておいてください。キーで実行できない操作が計画に残っていれば、`plan` が警告します（`V-B2`）。
- API キーは環境変数 `BACKLOG_API_KEY` から読み、それ以外からは読みません。`--api-key` オプションが無いのは
  意図的です。引数にすると `ps`、シェルの履歴、CI のコマンドログに見えてしまいます。

### セキュリティ：誰がスペースを変更できるか

> **マニフェストを置いたリポジトリへの push 権限は、CI に置いた API キーの持ち主の権限に等しくなります。
> それがスペース管理者のキーなら、スペース管理者の権限です。**

マニフェスト、あるいはそれを実行するワークフローに変更を push できる人は、そのキーが届く任意のプロジェクトの
設定を書き換えられます。ツール内部の検証ではこれを防げません。資格情報をどこに置くかで決まる性質だからです。

マニフェストのリポジトリはそれに見合うように守ってください。CI が適用するブランチにはレビューを必須にし、
ワークフローファイルを編集できる人を絞り、キーは用が足りる一番狭いシークレットのスコープに置きます。

## インストール

```sh
npx @simochee/backlog-blueprint --help
```

グローバルにインストールするものはありません。CLI はローカルでも CI でも `npx` から実行する想定です。

## クイックスタート

マニフェストを書きます。1行目のコメントが、エディタでの補完と検証を有効にします。
詳しくは下の [JSON Schema](#json-schema) を参照してください。

```yaml
# yaml-language-server: $schema=https://simochee.github.io/backlog-blueprint/schema/0.1.0/project.json
key: PROJ_A
name: プロジェクトA

issueTypes:
  - name: タスク
    color: "#7ea800"
  - name: バグ
    color: "#990000"
    templateSummary: "【不具合】"
  - name: 調査
    oldname: その他
    color: "#2779ca"

statuses:
  - name: 未対応
  - name: 処理中
  - name: レビュー中
    color: "#3b9dbd"
  - name: 処理済み
  - name: 完了

access:
  teams:
    - 31 # 開発チーム
  members:
    - 12 # 鈴木 花子

webhooks:
  - name: Slack 通知
    hookUrl: ${SLACK_WEBHOOK_URL}
    events:
      - issueCreated
      - issueUpdated
```

Backlog に一切触れずに確認します。

```sh
npx @simochee/backlog-blueprint validate -f projects/PROJ_A.yaml
```

ツールをスペースに向けて、何が起きるかを見ます。この例では `PROJ_A` は既に存在し、課題はありません。

```sh
export BACKLOG_SPACE=example.backlog.com
export BACKLOG_API_KEY=...
export SLACK_WEBHOOK_URL=https://hooks.example.com/T000/B000

npx @simochee/backlog-blueprint plan -f projects/PROJ_A.yaml
```

```
Blueprint: PROJ_A (example.backlog.com)

  ~ issueType      "バグ"
      templateSummary: (none) -> "【不具合】"
  ~ issueType      "調査"  renamed from "その他"
  - issueType      "要望"
  + status         "レビュー中"  color "#3b9dbd"
  ~ statusOrder    未対応, 処理中, レビュー中, 処理済み, 完了
  + projectTeam    "開発チーム"
  + projectMember  "鈴木 花子"
  + webhook        "Slack 通知"  hookUrl "https://hooks.example.com/T000/B000"

Warnings:
  ! [V-A16] access.members: "鈴木 花子" (12) already joins the project through the team "開発チーム"
      remove 12 from access.members to save one request. leaving it there also works

Plan: 4 to add, 3 to change, 1 to destroy, 5 unchanged.
Write requests: 8 (estimated 8s)
```

それから実行します。

```sh
npx @simochee/backlog-blueprint apply -f projects/PROJ_A.yaml
```

`apply` は同じ計画を表示して確認を求め、書き込みのリクエストを1件ずつ実行します。

上の計画に含まれていないものに注目してください。課題種別は1つも作成されていません。Backlog がプロジェクトと一緒に
作った4つのうち3つは残り（そのうち1つは `oldname` でその場で名前が変わります）、使われない4つ目だけが削除されます。
まだ存在しないプロジェクトでは事情が違います。既定の名前を前もって知ることができないので、`issueTypes` の最初の4つが
既定の4枠を引き継ぎ、それぞれ1リクエストかかります。どちらにしても、実行にかかる時間を一番左右するのはマニフェストの
書き方です。理由は [Writing a manifest](docs/manifest.md) で説明しています。

## コマンド

| コマンド       | Backlog への接続 | API キー | 用途                                         |
| -------------- | ---------------- | -------- | -------------------------------------------- |
| `validate`     | しない           | 使わない | マニフェスト単体を検査する                   |
| `plan`         | 読み取りのみ     | 必須     | `apply` が何をするかを見せる                 |
| `apply`        | 読み取りと書き込み | 必須   | 計画を実行する                               |
| `export <key>` | 読み取りのみ     | 必須     | 既存のプロジェクトをマニフェストとして書き出す |

`validate` と `plan` の違いは1つだけ、Backlog に問い合わせるかどうかです。`validate` はエディタでの確認と、API キーも
`${ENV}` で参照する値も持たない CI ジョブでのプルリクエスト検査のためのものです。スペースが見えないので、既定の状態、
既存のメンバー、課題数については何も言えません。

検証に失敗すると、どのコマンドも最初の書き込みの前に止まり、最初の1件だけでなく見つけた問題をすべて報告します。

### オプション

| オプション           | 環境変数        | 既定値 | 対象                      | 意味                                        |
| -------------------- | --------------- | ------ | ------------------------- | ------------------------------------------- |
| `-f, --file <path>`  |                 |        | `validate` `plan` `apply` | マニフェスト。`-` で標準入力から読む        |
| `--space <domain>`   | `BACKLOG_SPACE` |        | すべて                    | 例：`example.backlog.com`                   |
| `--output <format>`  |                 | `text` | `validate` `plan` `apply` | `text` または `json`                        |
| `--no-color`         | `NO_COLOR`      |        | すべて                    | 色付きの出力を無効にする                    |
| `--show-unchanged`   |                 |        | `plan`                    | 既に一致しているリソースも一覧に出す        |
| `-y, --auto-approve` |                 |        | `apply`                   | 確認のプロンプトを飛ばす                    |

`-f` は1回だけ指定でき、`export` はプロジェクトキーをちょうど1つ取ります。1つのマニフェストが1つのプロジェクトで、
1回のコマンドが扱うのは1つのプロジェクトです。複数を処理するときはシェルでループしてください。

`--output json` のとき、標準出力には JSON 文書しか出ないので、そのまま `jq` に渡せます。進捗、警告、エラー、
確認のプロンプトは標準エラーに出ます。

`apply` は既定で確認を求め、`yes` と全部打った場合しか受け付けません。標準入力が端末でなく `--auto-approve` も
指定されていなければ、誰も打たない答えを待たずにエラーで止まります。

### 終了コード

| コード | `validate`                         | `plan`         | `apply`                    | `export`     |
| ------ | ---------------------------------- | -------------- | -------------------------- | ------------ |
| 0      | 通過                               | 変更なし       | 適用した                   | 書き出した   |
| 1      | 検証エラー、またはその他の失敗     | エラー         | エラー（中断した実行を含む） | エラー     |
| 2      | —                                  | 変更がある     | —                          | —            |

`plan` が 2 を返すことが CI で役に立ちます。出力を解析しなくても、「マニフェストがスペースと一致している」と
「マニフェストが何かを変える」を区別できます。

### 既にあるプロジェクトから始める

`export` はプロジェクトを読み、マニフェストとして書き出します。組織のテンプレートを白紙からではなく、
うまく回っているプロジェクトから始められます。

```
$ backlog-blueprint export PROJ_A > projects/standard.yaml
```

標準出力には YAML しか出ないので、リダイレクトすればそのままファイルになります。それ以外はすべて標準エラーに出ます。
すべての読み取りが成功しない限り何も書き出さないので、失敗しても半端なマニフェストが残ることはありません。

結果を使う前に知っておくべきことが2つあります。

- **Webhook の URL が含まれます。** `export` は Backlog が返した値をそのまま書きます。環境変数から与えたい値は、
  自分で `${NAME}` に置き換えてください。コミットする前に生成されたファイルを確認してください。
- **元のプロジェクトには課題があって構いません。** `export` は読むだけなので、どのプロジェクトもテンプレートにできます。
  ただし、そのマニフェストを同じプロジェクトに適用し直すのは別の話です。課題を持つプロジェクトは `plan` も `apply` も
  やはり拒否します。先に `key` と `name` を変えてください。テンプレートを使い回すならどのみちそうするはずです。

[このツールがしないこと](#このツールがしないこと) に書いたとおり、これはドリフト検知ではありません。`export` が
終わった後にプロジェクトを見張るものは何もありません。

### `apply` が途中で止まったとき

ロールバックはありません。削除できないリソースがあるため、自動で元に戻そうとしても、別の壊れ方をしたプロジェクトが
できるだけです。代わりに `apply` は失敗したリクエストで止まり、適用したもの、失敗したもの、試みなかったものを表示します。

同じマニフェストをもう一度実行すると、止まったところから続きます。適用済みの作業は認識されて飛ばされるからです。
これはその時点でもプロジェクトに課題が無いことが前提です。その間に誰かが課題を登録すると、実行は検証で止まり、
そのプロジェクトはこのツールで管理できなくなります。

## Web UI

同じ検証と計画のコードが、ブラウザでも **<https://simochee.github.io/backlog-blueprint/>** で動きます。何かを
インストールするより YAML を貼り付けたい人のためのものです。裏にサーバーの無い静的なページで、ブラウザから直接
Backlog API と通信します。スペースと API キーは、再読み込みのたびに聞き直さなくて済むようにタブのセッション
ストレージに保存します。タブより長く残る場所には書かず、**Disconnect** を押すとすぐに消えます。

最初に API キーで接続します。接続中のスペースとユーザーは右上に表示され、別のスペースへの切り替えもそこで行います。
その後は1つのエディタで作業します。マニフェストを貼り付けるかドロップするか、**Open** でファイルを開き、**Plan** と
**Apply** を押します。**Save**（または Cmd/Ctrl+S）は、Chromium 系のブラウザでは開いたファイルに書き戻し、
それ以外ではコピーをダウンロードします。**Import from Backlog** は既存のプロジェクトを読み、`backlog-blueprint export` が
出すのと同じ YAML をエディタに開きます。新しいプロジェクトに対して plan する前に、`key` と `name` を変えてください。

## JSON Schema

スキーマは Web UI と一緒に、リリースしたバージョンごとに1つの URL で公開しています。

```
https://simochee.github.io/backlog-blueprint/schema/<version>/project.json
```

URL のバージョンは CLI のバージョンで、古い URL は消しません。何年も前に書いたマニフェストでもエディタが
動き続けます。`# yaml-language-server: $schema=...` のコメントで指すと、補完、インラインのドキュメント、
綴り間違いへの赤い波線が得られます。ただし、スキーマは権威ではなく補助です。CLI はスキーマでは表現できない
多くの検査を行うので、エディタが問題ないとしたマニフェストでも拒否されることがあります。
